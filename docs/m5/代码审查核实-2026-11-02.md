# 代码审查报告核实与修复清单（2026-11-02）

对象：`XSearch-代码审查-2026-11-02.md`（R01–R25、资源清单、5 个风险点）。

## 1. 结论

- **25 项全部存在**，没有误报；其中 R02、R19、R15、R16 的部分说法偏重或影响较小（见 §3）。
- **风险点**：第 2、3、5 项成立（第 3 项有一处说法偏重）；第 1 项（自反馈循环）**未复现**，但查出了另一个真实问题；第 4 项（UTI 测试失败）是报告运行环境造成的，不是产品缺陷。
- **优先级需要调整**：报告认为“没有 P0”，核实后建议把两项提到最高：
  - **R06 实测比报告严重**：空闲时 `IndexService` 持续占用约 35% 的单核 CPU。
  - **R05 会让应用崩溃**：越界抛 `NSRangeException`，报告写的是“未触发实际 UI 崩溃”。
- **报告遗漏 1 项**：整盘模式下，空闲时每秒约 3 次写入并 fsync 数据库（§4 N1）。

| 项 | 结论 | 说明 |

| 1. FSEvents 自反馈 | **未复现循环**，但有真实写盘问题 | 见 N1 |

## 4. 报告未列出的问题

- **N1（P1，实测）空闲时反复写盘**：整盘模式监听 `/`，系统任何文件活动都会回调；`received()` 即使过滤后 `ops` 为空，也会写 `fsevents_last_id`，且 `synchronous=FULL`，等于每秒约 3 次写入加 fsync，影响 SSD 寿命和耗电。
- **N2（P2，源码）**：上面 R25 提到的 `swift build` 判断问题。

## 5. 修复清单

规模：S = 几行到几十行；M = 一个模块；L = 跨层改动。

### 第 0 批：立刻修（改动小、收益最大）

- [x] **R06-a（S）** `FileCatalog.migrations` 增加 v3：`CREATE INDEX IF NOT EXISTS files_content_state ON files(content_state) WHERE deleted = 0 AND in_content = 1`。已测 56.67 ms → 0.04 ms。
- [x] **R06-b（S）** `cycle()`：先用只读 `SELECT 1 FROM content_tasks WHERE state = 0 AND not_before <= ? LIMIT 1` 判断，没有任务就不进 `BEGIN IMMEDIATE`；`refreshCounts` 只在本轮处理过任务或距上次超过 30 秒时执行。
- [x] **N1（S）** `received()`：`ops` 为空时只在内存里更新游标；有真实操作时写入，30 秒定时器和退出时补写。重启后重放的事件会被再次过滤，无害。
- [x] **R05（S）** `PreviewPane`：`go(to:)` 和 `render` 全部使用 `NSIntersectionRange(target, shownRange)`；交集为 0 才移动窗口；上色、`ensureLayout`、滚动都用交集；超长命中显示“命中超出显示范围”。把裁剪算法抽成纯函数放进 ContentEngine 以便测试，覆盖超长命中、跨窗口命中、组合字符。
- [x] **R25 / N2（S）** `regression.sh`：直接判断 `cargo test`、`swift build` 的退出码（`set -o pipefail`，去掉 `|| true`），日志过滤只用于显示。
- 验收：空闲时 IndexService CPU < 1%；WAL 空闲时不再每秒变化；`regex:a+` 配合 `dir:` 在 40 万字符文本上不崩溃。

**第 0 批结果（已完成）**

| 项 | 修复前 | 修复后 |
|---|---|---|
| IndexService 空闲 CPU | 约 35% 单核 | 约 60 秒用 0.05 秒（< 0.1%） |
| 两条统计 SQL | 56.67 ms/轮，每 0.5 秒 | 0.04 ms，只在处理过任务或每 30 秒执行 |
| 空闲时的写锁 | 每 0.5 秒 `BEGIN IMMEDIATE` | 没有任务时不取写锁 |
| 数据库写入 | 约每秒 3.5 次（只为保存游标） | 约每秒 0.3 次；复核的 30 秒内应用了 28 条真实日志操作，来自索引范围内的真实文件变化 |
| R05 | 真实应用崩溃（崩溃栈：`PreviewPane.go(to:)` → `addAttributes:range:` → abort） | 不崩溃，显示“命中过长，只显示开头” |
| 回归脚本 | 吞掉退出码；构建失败后可能跑旧二进制 | 以退出码为准；`regression.sh` 通过，73 项指标在范围内 |

另外修了 `rebuildSwitchesInstanceAfterCatchingUp` 的时序竞争（整套测试并行时偶发失败，与本次改动无关，改动前的代码单独运行也不失败）：改为在重建提取过程中检查旧实例可读。修复后连跑 4 次全套测试，无失败。

说明：游标保存改为内存优先。进程崩溃时最多丢失 30 秒内只含无关事件的游标，重启后这些事件会被重放并再次过滤。

### 第 1 批：索引一致性

- [x] **R01（M）**
  1. `purgeTombstones` 增加 `AND NOT EXISTS (SELECT 1 FROM content_tasks t WHERE t.file_id = files.id)`；
  2. `process()`：`contentInfo == nil` 时返回 `.remove`（靠 op_seq 围栏保证幂等），不再 `.drop`；
  3. `stageAndCommit` 复核改为 `LEFT JOIN files`：行不存在时只校验租约；
  4. 清理历史残留：启动时用 `appliedSeqs()` 的 file_id 对比 `files`，一次性删除孤儿文档（用 meta 标记只做一次）。
  - 回归测试：停索引器 → 删除 → 清墓碑 → 重启后搜不到。
- [x] **R02（M）** 不需要状态机，保证原子性即可：
  1. 先生成 id、打开新 writer（崩溃只留下孤儿目录）；
  2. 同一事务内写 `content_rebuild_instance`、全量 requeue、清空 `content_batch`、重置 `content_batch_pending` 和 `content_batch_confirmed`；
  3. 启动时删除既不是活动实例也不是重建实例的目录；
  4. 旧目录延后到下次启动或数分钟后回收，给读者留出切换时间。
  - 测试：在每一步之间注入崩溃，都不能发布空索引。
- [x] **R03（M）** 把 `recover()` 拆成可复用的恢复函数：`cycle` 的一般异常分支执行 rollback → 按 `lastCommit` 处理未确认批次 → 释放本进程租约 → 记录错误并退避 5 秒（避免空转）。`claim` 同时领取 `state = 1 AND lease_until < now`。测试：注入 SQL 错误，恢复后无需重启即可继续。
- [x] **R04（M）**
  1. `stopped` 改为加锁或原子标志，`stop()` 先置位；
  2. `ExtractionWorker` 增加不依赖 `extract` 锁的 `cancel()`，直接杀当前进程；
  3. 被停止导致的失败不计入 attempts；
  4. 循环在每个文件、每批之后检查；
  5. `Service.stop` 不持锁等待；
  6. 客户端退出最多等 2 秒，其余留给下次恢复。
  - 验收：同样的探针 `stop()` < 0.5 秒。
- [x] **R07 + R14（L）** 新增一次调用返回文档和高亮的 FFI（同一 searcher，修复 R14），先做第一步：
  1. 限制：只为最多 N 处命中建立映射（例如 1 万），用 `normalize_prefix` 只处理到最后一处，总数另行统计；
  2. 压缩包：先按成员切片再计算高亮；
  3. 之后再按窗口按块生成映射。
  - 验收：100 MiB 正文预览峰值 < 500 MB。阅读窗口入口同时传 `MatchMode`。

第 1 批结果（探针已转成正式回归测试，见 `IndexerTests.swift` 的 Consistency 部分和 `engine.rs`）：

| 项 | 修复前 | 修复后 |
|---|---|---|
| R01 | 停索引器 → 删除 → 清墓碑 → 重启，旧词仍能搜到 | 搜不到；有任务的墓碑不再清除；一次性清理历史孤儿文档 |
| R02 | 中断的重建会上线空索引 | 重建标记和全量排队在同一事务；中断后继续重建，全部内容可搜；未知目录启动时回收；旧实例保留 60 秒再删 |
| R03 | 过期租约永远卡住；SQL 错误后要重启才恢复 | 过期租约重新领取；出错退避 5 秒后自动恢复，设置页显示“正在自动重试” |
| R04 | 8 个卡死文件时 `stop()` 11.7 秒 | 测试上限 1 秒内返回，任务保留，attempts 不增加，重启后全部完成；客户端退出最多等 2 秒 |
| R07 | 100 MiB 正文高亮峰值 3.14 GB | 引擎侧峰值 **320 MB**（161 万和 484 万处命中都一样），约 0.3 秒；这是 Rust 引擎的数字，不含传给 Swift 后的文本副本 |
| R14 | 文档和高亮分两次读，可能不属于同一快照；压缩包先算全文高亮再切片 | 一次调用、同一 searcher；先切成员再算高亮；阅读窗口使用结果所属的匹配模式 |

实现和清单的差异：

- 高亮数量上限定为 5,000 处（清单举例为 1 万），界面显示“第 n/5,000 处（共 N 处）”，阅读窗口显示“前 5,000 处（共 N 处）”。
- 超过上限的命中无法在预览中跳转到。清单第 3 步“按窗口按块生成映射”没有做：现在的流式映射已经达到验收线。
- `recover` 不再比较 `content_batch_confirmed`，只看索引自身的提交记录。
- 客户端等待超过 2 秒后，服务仍在后台收尾。随后如果立刻执行“重建文件名索引”并删除目录，这段时间内存在重叠；取消提取后正常情况下收尾很快，只有数据库长时间繁忙才会发生。

没有做的部分：

第 1 批的遗留修复：`cancel()` 之后调用 `Process.waitUntilExit()` 偶尔永远不返回（进程已退出，但 run loop 等不到唤醒），回归测试因此挂起。杀进程后改为最多 1 秒的轮询，并加了压力测试，全套测试连跑 8 次无挂起。

升级影响：表格、PPTX、压缩包的提取器版本提高，升级后这三类文件会重新提取一次。纯文本超过上限时仍按原设计保留开头部分（状态为部分提取），其他类型超限后标记为失败。
