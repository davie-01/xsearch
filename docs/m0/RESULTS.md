## 3. 恢复验证覆盖

恢复验证器使用真实磁盘文件，不是只在内存中模拟状态。SQLite 使用 WAL + FULL synchronous；Tantivy 使用真实 writer、rollback、commit payload 与重新加载的 reader。

进程测试在以下 11 个点直接退出、不运行 Rust 析构，再由新进程打开同一目录恢复：

1. SQLite 已写操作日志与 catalog、尚未提交事务。
2. 事件、op_seq、任务与 source/content 游标事务已提交，名称未发布。
3. 名称快照及名称游标已发布，内容未提交。
4. 已领取任务租约。
5. 已写入 Tantivy 未提交批次。
6. 注入提交前失败并回滚后。
7. Tantivy 已提交、SQLite 尚未确认。
8. SQLite 已确认提交批次。
9. 新实例追平后、切换事务之前。
10. 实例切换 SQLite 事务进行中，尚未提交。
11. 实例切换事务已经提交。

另外验证：租约到期和重领、旧 worker 返回、提交前发生更新/删除、删除后同内容重新纳入、提取配置升级但字节不变、重建期间新旧实例各自记录同一操作、旧实例迟到任务、同一实例只有一个未确认批次、提交失败后序号表回退、结果不确定的成功/失败两条路径、低水位消费者与重建起点阻止日志过早清理。

M0 为串行协调器协议验证：以程序事件代表文件变化、范围和配置变化，尚未接入真实 FSEvents、inode 身份判定、生产 worker 调度和文件版本复核。事务内的多个 SQL 步骤利用原子提交合并故障边界；没有执行真实断电、磁盘耗尽或硬件故障实验。M1/M2 接入真实组件时必须保留这些测试并增加端到端测试。

## 4. 验证发现及已落实的修正

**统一 Unicode 实现。** 初版 Swift Foundation 独立实现，在 54,408 组对照中出现 99 组差异。即使共享大小写折叠表，系统分解表仍有 4 组差异。现在使用 Rust 的 Unicode 17.0.0 分解与全折叠实现，经 C ABI 返回规范化文本及源 scalar 映射；Swift 负责 UTF-16/PDFKit 对接。索引打开时校验 `norm_ver`，版本不兼容必须重建。不能因为常用中英文样本通过，就假定两个语言的系统 API 行为相同。

**收窄前检查 NFC 后的实际名称键。** `cafe` 追加组合重音后变成 `café`，结果不一定是旧结果子集。原始输入前缀相同不是充分条件；还要有规范化后的包含证明以及相同索引版本、选项、范围和完整旧结果集。

**保留删除序号，提交时再检查有效性。** 删除后只保留最小墓碑，正文和锚点不进入墓碑。未提交批次在发布前复核最新 op_seq 与租约；租约过期但仍是最新操作的任务重新排队，不能当成已被替代而丢失。提交失败时回滚并重建持久化序号表；无法确认 writer 状态则阻止继续写入直到重新打开。

**PDF 有文本不等于文本完整。** 合成 PDF 中 `𠀀` 经当前字体/文字层转换后变成 NUL。现在该页明确标记 `partial_text`，保留原文以免破坏坐标；空白文字层标记 `waiting_ocr`。真实 104 页 PDF 未检测到 NUL/替换字符。此启发式不能检测所有阅读顺序或字符映射错误，后续仍需质量诊断与 OCR。

## 5. M0-B 可选优化对比

M0-B 只决定选哪种方案，不改变正确性规则。每项都附带与暴力扫描或完整结果的对照，没有明显收益的优化不采用。所有计时为单机顺序执行、无统计置信区间；不在同一时间运行 OCR、构建或其他基准。公开数字与源码哈希见 `docs/m0/M0B-EVIDENCE.json`，其中不含正文、图片、真实文件名或路径。

### 5.1 内容召回（2026-10-29）

固定同一批 12 份真实文本，UTF-8 正文总计 **291,722 字节**。每个方案使用新索引目录；先预热 10 条查询，再将这 10 条查询各重复 10 次，共 100 次。计时包括召回、可选布隆读取、stored text 读取、归一化和精确核验，不包括文件提取、UI 或 XPC；并非冷缓存测试。

| 方案 | 索引字节 | 建库 ms | P50 ms | P95 ms | 100 次累计候选 / 核验 |
|---|---:|---:|---:|---:|---:|
| 字节 trigram，2 字节前缀区间 | 287,238 | 76 | 5.020 | 10.187 | 450 / 450 |
| 字节 trigram，2 字节范围扫描 | 287,238 | 75 | 4.909 | 10.334 | 620 / 620 |
| 字节 trigram + 独立 fast-field 布隆 | 366,954 | 77 | 4.170 | 10.513 | 450 / 430 |
| 字符 1/2/3-gram | 625,806 | 108 | 4.370 | 10.982 | 430 / 430 |

字符方案同时保存 1/2/3 字符项，不是只保存三字符项；索引体积包含 Tantivy 文件与固定开销，不能拿来当整个磁盘文件体积的固定倍率。结论：**字节 trigram**（字符方案约 2.18 倍空间，没有稳定延迟优势）；**2 字节默认前缀区间 + 末尾特殊项**（减少候选，保留扫描路径作成本切换对照，此样本不足以给出自动切换阈值）。

### 5.2 布隆预筛：实际解压量

上次只统计了逻辑正文字节。本次在独立 bench workspace 中给 Tantivy 0.27.0 `StoreReader` 的缓存未命中解压路径插桩（`scripts/prepare-store-instrumentation.py` 记录原文件与插桩后哈希），直接计数解码输入字节与解码块数。共 352 次布隆开/关与完整结果对照，命中数全部一致，没有漏召回。

| 语料（新 store 缓存） | 查询 | 候选 | 核验（关 → 开） | 解码输入字节（关 → 开） | 最大 P95 ms（关 → 开） | 索引字节（关 → 开） |
|---|---:|---:|---:|---:|---:|---:|
| 真实 12 份 | 16 | 82 | 82 → 78 | 1,445,217 → 1,402,083（−3.0%） | 10.79 → 10.40 | 287,232 → 366,948（+27.8%） |
| 构造的 trigram 误报语料 | 6 | 3,072 | 3,072 → 1,088 | 304,284 → 111,752（−63.3%） | 259.2 → 259.8 | 47,686 → 47,799 |

重复查询（warm）结果比例相同。真实语料上布隆只减少约 3% 实际解压量，却增加约 28% 索引体积；即使在专门构造、误报率很高的语料上解压量减少 63%，P95 也没有改善，说明这一环节不是延迟主因。**布隆继续默认关闭。** 只有当大库实测出现大量 trigram 误报、且解压成为瓶颈时再评估。

### 5.3 正文存储：Tantivy stored fields

对比 Zstd 16 KB 块（Tantivy 默认）、Zstd 64 KB 块、不压缩 16 KB 块；每种都测无块缓存与 100 块缓存，以及顺序、乱序、热点文档（同一文档读 128 次）三种模式，共 72 组。单次读取计时包括取出 stored 文档。

| 真实 12 份（291,722 字节） | store 字节 | 无缓存顺序读 P95 µs | 无缓存热点 P50 µs | 100 块缓存热点 P50 µs |
|---|---:|---:|---:|---:|
| Zstd 16 KB | 89,473（30.7%） | 213 | 35 | 15 |
| Zstd 64 KB | 87,617（30.0%） | 220 | 62 | 15 |
| 不压缩 16 KB | 292,037（100.1%） | 124 | 24 | 19 |

合成混合大小语料（19,014,208 字节、384 份）：Zstd 16 KB 为 7,938,319 字节（41.7%），64 KB 块体积几乎相同，不压缩为 19,021,546 字节；无缓存顺序读 P95 分别为 154、116、65 µs。

结论：**继续使用 Tantivy Zstd stored fields，保持 16 KB 块并启用 doc store 块缓存**。单次读取 P95 不超过 0.25 ms，远低于内容查询 200 ms 目标；64 KB 块几乎不省空间，热点文档读取反而更慢；不压缩约 3 倍体积，只换来约 0.1 ms。没有证据需要另建正文存储。

### 5.4 文件名布局

合成数据，各 10 万和 100 万条，两种极端分布：`unique`（每个名称不同）和 `high_repetition`（只有 256 个不同名称）。数据按打乱的顺序导入。四种布局：简单列式；目录块深度优先；目录块 + 名称驻留；再加每 64 个名称一组的字符类位图。每种都测纯快照和“快照 + 1% 增量层”（删除、移出、移入、改名、新增）。12 条查询覆盖中文一字/二字、英文子串、短 ASCII、数字、标点、AND、目录范围、嵌套目录、NFC、无结果以及字面 `sj`（不做拼音）。**576 次完整结果与全量扫描对照全部一致**，另有 NFC、无拼音、整棵子树移动的单元测试。

100 万条、纯快照，12 条查询 P50 的中位数 / 最大 P95 / 嵌套目录查询 P50 / 名称缓冲区：

| 布局 | unique | high_repetition |
|---|---|---|
| 简单列式 | 21.3 / 25.0 ms / 1,076 µs / 82.8 MB | 31.1 / 35.9 ms / 1,443 µs / 70.2 MB |
| 目录块 | 15.9 / 21.6 ms / 439 µs / 82.8 MB | 24.0 / 31.8 ms / 549 µs / 70.2 MB |
| 目录块 + 驻留 | 15.3 / 21.0 ms / 400 µs / 86.8 MB | **3.0 / 4.3 ms / 42 µs / 32.2 MB** |
| 目录块 + 驻留 + 位图 | 14.9 / 21.2 ms / 415 µs / 86.9 MB | 3.0 / 3.1 ms / 41 µs / 32.2 MB |

加上 1% 增量层后（目录块 + 驻留），P50 中位数 unique 从 15.3 升到 22.7 ms，high_repetition 从 3.0 升到 10.5 ms；100 万条合并一次约 1.6–1.9 s。建库时间目录块比列式多约 0.5–0.8 s（排序成本）。

结论：
- **采用目录块深度优先布局**：两种分布都更快，`dir:` 变成区间约束，嵌套目录查询快 2.5 倍以上。
- **采用名称驻留**：名称重复多时速度和内存都明显改善；名称全不同时只多约 5% 内存，速度不变。真实磁盘的不同名称比例在 M1 扫描时实测，不作为前提。
- **不采用字符类位图**：没有稳定收益。
- **增量层合并阈值应远低于 1%**：1% 增量已使查询明显变慢。M1 按条目数或时间在后台合并，合并完成后原子替换快照。
- 以上是单线程、内存内的引擎耗时，不含排序、UI 和真实扫描；100 万条最大 P95 约 21 ms，在“输入到首屏 80 ms”的目标内，但真实分布需 M1 复测。

### 5.5 XPC 往返延迟

签名主程序 → 应用内 XPC Service，在正常用户会话运行（自动化沙箱下无法 bootstrap）。0 / 64 / 4096 / 65536 字节负载，每档 500 次 × 3 轮，共 6,000 次；用 `mach_continuous_time` 记录到回调到达的时间。

| 负载 | 第 1 轮 P95 µs | 第 2、3 轮 P50 µs | 第 2、3 轮 P95 µs |
|---|---:|---:|---:|
| 0 字节 | 35.7 | 15.3–16.6 | 24.7–25.9 |
| 64 字节 | 31.3 | 15.3–19.5 | 24.3–27.5 |
| 4 KB | 31.1 | 19.7–22.5 | 28.3–30.3 |
| 64 KB | 52.1 | 45.6–46.0 | 51.0–51.4 |

首次连接（冷启动服务进程）建连 3.6 ms、首次往返 12.1 ms；之后的新连接建连 55–88 µs，服务进程被复用。

结论：稳态 XPC 开销是几十微秒，不构成延迟约束；冷启动约 16 ms，**IndexService 应在应用启动时预热**，不要等到第一次查询。名称引擎仍按设计放在 UI 进程内，避免冷启动和大结果集的序列化。

### 5.6 Vision 小实验

`VNRecognizeTextRequest`（revision 3）、accurate、`zh-Hans` + `en-US`、开启语言纠错。需在正常用户会话运行；自动化沙箱下返回 `nilError`。

**校准**：把一份有文字层的真实 PDF 前 10 页按 150 / 300 dpi 渲染后识别，与 PDFKit 文字层比较（文字层不是独立人工标注）。封面文字层不完整，不计入。
- 正文页（6–10 页）：字母和数字编辑距离 150 dpi 为 3 / 2,575，300 dpi 为 4 / 2,575。
- 目录页（2–5 页）：字母和数字基本都识别到（字符集合召回 ≥ 0.93），但引导点和版面使阅读顺序不同，含标点的整体错误率约 0.9。
- 全部可比页字母和数字错误率两种 dpi 都是 8.5%，300 dpi 没有更好。
- 耗时：第一次请求 12.3 s（模型冷加载）；之后每页 103–255 ms，渲染 5–7 ms。

**真实输入**（7 个来源、14 次识别，长边缩到 2000 px 与原分辨率各一次）：
- 3 张海报照片：人工抽查短语找到 28 / 29，两种分辨率结果相同。
- 2 份扫描表格（150 / 300 dpi）：短语 24 / 24，116 字正文段落 0 编辑。
- 2 张远距离拍摄的屏幕照片：识别出 0 个字符。
- 每次 160–450 ms。

对 M6 的结论：150 dpi / 长边 2000 px 是合适的起点；首次任务的冷加载约 12 s，要在 worker 中预热并显示进度；串行约 0.2 s/页；置信度不等于准确率；识别出 0 字的图片要显示“OCR 未识别出文字”而不是“没有结果”；目录、表格等版面的阅读顺序是主要弱点，M6 要对比 `RecognizeDocumentsRequest`。样本量小，只用于估计工作量，不作为质量承诺。

### 5.7 方案选择汇总

| 对比项 | 采用 | 不采用 / 待定 |
|---|---|---|
| 内容召回 | 字节 trigram | 字符 n-gram |
| 2 字节查询 | 前缀区间 + 末尾特殊项，保留范围扫描对照 | 自动切换阈值待大库确定 |
| 布隆预筛 | 默认关闭 | 大库出现大量误报且解压成瓶颈时再评估 |
| 正文存储 | Tantivy Zstd stored fields，16 KB 块 + 块缓存 | 64 KB 块、不压缩、独立正文存储 |
| 文件名布局 | 目录块深度优先 + 名称驻留 + 增量层（后台合并，阈值远低于 1%） | 字符类位图 |
| XPC | 稳态开销可忽略；IndexService 启动时预热 | — |
| 提取路线 | DOC：NSAttributedString，textutil 兜底；DOCX：Rust ZIP/XML | 原生 DOCX 备用提取覆盖片段更少 |
| OCR（M6） | 150 dpi 起步、worker 预热、0 字结果显示状态 | 版面结构 API 待 M6 对比 |

仍未测：百万文件的真实磁盘扫描与内容索引、冷缓存与内存峰值、真实文件名分布。这些不影响 M0-A 正确性验收，在 M1/M2 用真实组件测量。
