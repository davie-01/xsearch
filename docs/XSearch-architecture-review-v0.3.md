# XSearch v0.3 架构评审与修订建议

日期：2026-10-29。状态：评审建议，待用户确认；不是开工指令。

评审对象：`docs/ARCHITECTURE.md`。开始阅读时为 v0.2，过程中发现已更新到 v0.3，本文已纳入新增的分区、网络盘、完整窗口、收藏、邻近查询和格式扩展。未修改原文件，未开始应用开发。

**结论：保留 Swift/AppKit 原生界面、独立文件名索引、Rust/Tantivy 内容检索的总体路线；优先修正召回完整性、位置映射和增量一致性，同时削减首版的自研存储、分区和常驻服务复杂度。** 新增的 DocFetcher 和 MacHunt 提供了很有价值的对照，但没有充分理由让 XSearch 整体转向 Java/Lucene 或 SQLite FTS5。

本文区分三类结论：源码或官方资料可以确认的事实、面向 XSearch 的设计建议、必须通过原型实测才能定案的性能假设。没有运行四个完整应用做同机性能对比，也没有把 README 的数字当作 XSearch 的测试结果。

## 1. 四条技术路径分别解决什么问题

| 项目 | 已核对的实现路径 | 值得借鉴 | 对 XSearch 的适用边界 |
|---|---|---|---|
| oil-find | Swift/AppKit；批量目录扫描；紧凑列式文件名数据；C/NEON 匹配；FSEvents；查询收窄 | 文件名热路径、原生启动器、拼音、扫描与索引布局 | 公开仓库主要提供文件名能力；Pro 内容搜索不应视为可直接参考的公开实现 |
| pivotsearch | Rust/Tantivy；解析器注册；jieba 与停用词；目录更新任务；正文预览按需加载 | Rust 模块组织、解析器接口、索引写入流程 | 不满足任意子串完整召回；解析覆盖、分页合并、增量可靠性需独立设计 |
| DocFetcher | Java/SWT；Lucene；POI/PDFBox 等解析库；指定目录索引；文本预览 | 内容库管理、范围筛选、格式能力矩阵、文档查阅流程 | 词项检索与原文件重解析预览不等于任意子串检索；不建议为首版引入 JVM |
| MacHunt | Rust；SQLite FTS5 trigram；WalkDir；FSEvents；Tauri/React；CLI 共用核心 | 数据库式元数据管理、批量写入、过滤条件、诊断与命令行验证 | 当前主要是名称搜索；中文/短查询回退扫描，不能直接替代 XSearch 的内容搜索方案 |

来源：[oil-find 项目说明](https://github.com/oil-oil/oil-find)、[pivotsearch 项目说明](https://github.com/alrece/pivotsearch)、[DocFetcher 官方源码入口](https://sourceforge.net/p/docfetcher/code/ci/master/tree/)、[DocFetcher FAQ](https://sourceforge.net/p/docfetcher/wiki/FAQ/)、[MacHunt 项目说明](https://github.com/dacj4n/MacHunt)。

源码核对范围：读取本机已有的 oil-find、pivotsearch、MacHunt 源码快照，并用公开网页核对项目路径与关键设计。oil-find 本地 checkout 为 `e63c7150ccbd401a1375c08215d1386b56dd9471`；另两个本地快照未取得可核验的提交号，因此不宣称逐文件对应线上最新 HEAD。DocFetcher 官方仓库入口显示提交 `1a22d23a029d2368c821ea39c0ddbcf44f91c202`，查阅了官方依赖目录、构建说明、介绍和 FAQ；其内部 Java 文件未能通过当前网页工具完整获取，不宣称已逐函数审计。

几个会影响选型的源码细节：

- oil-find 的 `IndexStore+Persistence.swift` 使用 mapped data 读取后，通过 `memcpy` 复制到可变索引。因此“持久化文件可映射读取”与“零复制可变索引”是两回事。XSearch 首版可以采用前者，不必一开始设计可变 mmap 文件。
- oil-find 的 `Searcher.canNarrow` 检查索引版本、选项与查询条件是否允许收窄。不能只判断输入字符串是否延长，更不能只在屏幕上的前 9 条结果里筛选。
- pivotsearch 的 `tokenizer.rs` 明确过滤“的”“可以”“的话”等词；`schema.rs` 不存完整 content，但另存 snippet 前缀。原方案判断应保留：不能直接复用其召回语义。
- pivotsearch 的 DOCX 解析器主要遍历顶层正文段落；XSearch 必须补充表格等覆盖测试。[DOCX 源码](https://github.com/alrece/pivotsearch/blob/main/crates/parser/src/docx.rs)
- 本地 pivotsearch 的 `search/multi.rs` 自行遍历多个搜索器并拼接结果，子请求固定第一页；这不是可直接复用的全局排序分页方案。
- 本地 MacHunt 的 `db.rs::search_fts` 对 `字符数 <= 3`、非 ASCII 或含非字母数字的查询使用 LIKE/GLOB 路径。其 README 用“少于 3 字符”概括，源码条件更宽。

**不能把 MacHunt 的回退策略误读为 SQLite 不支持中文 trigram。** SQLite 官方规则是：FTS5 trigram 的全文 MATCH 对不足三个 Unicode 字符的子串不匹配。本次在内存数据库中以 SQLite 3.54.0 验证，`共享交`、`foo-bar`、`User`、`2202` 能命中，`共享`、`据`不能。这只验证分词语义，不是性能测试。三字中文、标点都不是它天然不支持的对象。[SQLite FTS5 trigram](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)

## 2. 先修正产品承诺：搜索准确包含四个不同问题

目前“任意子串零漏检”覆盖范围太宽。建议改成：

> 对用户选择的索引范围内、已成功且完整提取的文本，在明确的归一化规则下，字面子串检索不因分词或候选截断漏检。未索引、提取失败、部分提取、文件已变化和 OCR 识别不确定分别展示状态。

这不是降低要求，而是让要求可以逐层验收：

| 层次 | 应证明什么 | 常见误区 |
|---|---|---|
| 文件发现 | 应纳入的文件都被发现；排除项和无权限可见 | 文件没被扫描却显示“没有结果” |
| 文本提取 | 表格、文本框、页眉等按支持声明被提取 | 文件打开成功就算全文完整 |
| 检索召回 | 真实匹配一定进入候选，核验与分页不丢结果 | 只对候选做精确核验便宣称零漏检 |
| 预览定位 | 命中区间能映射回正确版本的文本和页面 | 只存页码就承诺字符级高亮 |

OCR 无法保证原图上的每个字都识别正确。需要展示 OCR 来源、识别配置和可重识别状态，而非将“识别文本上的精确匹配”说成“原文件零漏检”。

## 3. 内容检索：从混合分词改为明确的字面检索通道

### 3.1 当前方案的具体漏洞

正文包含 `getUserName`，用户搜索 `serNa`；正文包含 `622202123456`，搜索 `2202`。按英文单词或代码驼峰拆分，仍不能保证这些子串被召回。新增标识符拆分改善的是按组成词查询，不是任意位置的子串。

中文“单字 + bigram + PhraseQuery”也不是自动正确：必须规定单字、双字的 position、position_length、跨标点与跨脚本边界。Tantivy 内置 NgramTokenizer 的 position 始终为 0，不能直接当作字符位置短语索引使用。[Tantivy NgramTokenizer 源码](https://docs.rs/tantivy/latest/src/tantivy/tokenizer/ngram_tokenizer.rs.html)、[PhraseQuery 文档](https://docs.rs/tantivy/latest/tantivy/query/struct.PhraseQuery.html)

### 3.2 推荐首版方案

保留 Tantivy，自行控制字面查询规划：

1. 保留原始提取文本作为显示文本，按统一规范生成检索文本。
2. 对检索文本生成跨文字类别的字符 n-gram，包含中文、英文、数字和需要保留的标点，不先按词截断。
3. 长查询以三字 gram 的交集召回；两字查询用双字 gram；单字查询用单字通道。
4. 从候选读取文本并核验完整查询表达式，生成真实命中范围。
5. 首屏满足后继续按需分页；任何预算耗尽都标记“仍在搜索”或“不完整”，不能悄悄当作最终无结果。

单字、双字索引可只记录文档是否包含该 gram，减少位置成本；高频短查询仍会产生大量候选，必须单独测试。三字 gram 是否保存位置、是否使用字符位置 phrase 优化，在原型中比较，不先写死。

不必同时把 unigram、bigram、trigram 的所有位置都存一遍。也不要为了减少索引体积，把短查询悄悄改成只搜文件名。

默认用户语义建议为：`foo bar` 表示同一文件包含两个字面子串；`"foo bar"` 表示连续短语；`|` 为或；排除词为 NOT。精确核验必须执行同一份查询 AST。对于 NOT，不能直接减去“可能命中排除词”的近似 gram 候选，否则会误排真实结果。

增加明确的“区分大小写”“严格原文”选项。NFKC 会把一些兼容字符合并，适合宽容搜索，但应避免将该行为冒充原字符严格相同。代码搜索需要保留符号，不默认删除标点。

`content_word` 可以用于排序或可选词语检索，不能成为字面召回的唯一入口。首版无需增加语义向量检索；它解决“意思相近”，不能替代定位某个确切文件内容。

### 3.3 两阶段搜索的性能约束

按“候选文件 → 解压全文 → 找全部命中 → 排序”处理所有文件，会把高频查询拖成批量读取。建议按以下顺序设计：

- 目录、类型、时间、大小条件尽量在候选阶段收窄。
- 候选分批核验，首屏只生成必要 snippet；完整命中列表在选中文件后计算。
- 不将候选 Top 100 截断后再核验当成最终答案；过滤掉假阳性后需要继续补候选。
- 用查询 ID、取消令牌和索引 generation 丢弃过期结果。
- 如后期将长文件切块，明确文件级 AND：两个词分别位于不同块也应命中文件；跨块短语需要重叠/边界索引或额外路径，固定长度重叠不能覆盖无限长短语。
- 核验阶段需要显式遵守工作预算；先显示已验证结果，最终总数只能在完成后给出。

邻近查询后置。v0.3 的“相距 10 个字”不能直接等同 Tantivy phrase slop：应明确按 Unicode 字符、词元还是字符间隔计数，是否有序，是否允许跨段落。

## 4. 存储：首版不用自研 pack 文件

目前同时设计 Tantivy、zstd pack TextStore、SQLite 三套持久化，开发成本不仅是写入，还包括索引与文本一致性、压缩块寻址、空间回收、崩溃恢复、版本迁移和并发读者生命周期。

**建议保留 TextStore 这个接口，首版由 Tantivy stored fields 实现。** 官方存储已经提供压缩的文档字段存取，可选 LZ4/Zstd；具体功能按锁定版本核对。[Tantivy store](https://docs.rs/tantivy/latest/tantivy/store/index.html)

建议保存：

| 数据 | 首版位置 | 用途 |
|---|---|---|
| 原始提取文本 display_text | Tantivy stored field | 预览、精确核验、重建检索字段 |
| 提取结构与来源映射 | Tantivy stored bytes | 页码、段落、单元格、OCR 框定位 |
| gram 与可选词项 | Tantivy indexed fields | 召回与排序 |
| 文件逻辑 ID、内容修订号、提取器版本 | Tantivy stored/indexed 字段 | 对应同一份文本与索引 |
| 文件发现状态、范围、任务、错误 | SQLite | 调度与覆盖率 |
| 收藏、历史、个人偏好 | SQLite 独立表或独立 user.sqlite | 重建索引时保留 |

归一化文本和归一化到显示文本的映射可按文档生成并缓存；若实测 CPU 成本明显，再额外持久化。不要在没有评估前同时保存多份完整正文。

stored fields 不保证超大文件的任意局部读取都廉价。因此原型必须测大 PDF、大日志、映射体积与取消延迟。只有测出瓶颈，才引入按页/文本块读取的独立存储后端；先用成熟数据库 BLOB 也比立刻自制 pack 更容易恢复。不得仅因为“正文不要存在倒排索引里”就否定 Tantivy 的独立 stored-field 机制——索引词项和存储正文是不同配置。

这一调整让“本次可搜索文本”和“本次可预览文本”随同一个 Tantivy commit 发布。SQLite 仍需恢复协议，但不再额外同步第三套文本文件系统。

## 5. 增量更新与崩溃恢复必须成为正式架构

### 5.1 文件身份和事件游标

增加稳定的逻辑 `file_id`，不要只把 path 当身份。卷 UUID、文件系统 ID/inode、创建/出生信息和当前路径共同辅助身份判断；inode 会复用，原子替换会换 inode，硬链接会有多条路径。

至少区分三种版本：文件内容修订号、提取器/归一化版本、索引 generation。仅 mtime 不够；结合纳秒时间、大小、事件脏标记，必要时校验哈希。事件已提示变化时，不应因 mtime 和 size 恰好相同就忽略。

FSEvents 是变更线索，不是永久完整日志：

- 建立 watcher 与初始扫描之间需要明确水位和回放，避免扫描期间发生变化却漏掉。
- 游标在“变更已持久进入任务队列或名称快照”之后推进，不能收到事件就算处理完毕。
- 队列按 `file_id + revision + task_type` 去重；正在处理时又变化，应留下新修订任务。
- 增加 RootChanged、EventIdsWrapped、丢事件、历史不可回放、挂载/卸载处理。
- 子树聚合事件按对应子树重扫；明确的事件丢失按受影响的监控范围扩大重扫，不能假定只重扫单个叶子目录足够。
- 对账失败或无权限不能当作目录为空，不能据此删除旧索引。
- 网络盘只保证可解释的最终一致性；挂载发现不等于盘内更新检测，应定时核对并显示上次成功时间。

Apple 对事件合并、丢事件与根变化的处理有明确说明。[FSEvents 指南](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html)

### 5.2 建议的提交协议

1. SQLite 记录待处理 revision、任务状态与持有期限。
2. worker 完成提取；前后重新核对文件版本。文件变动则丢弃旧提取结果并重排。
3. 索引服务以稳定逻辑 ID 幂等更新文档，文本、映射与词项一起提交；commit payload 记录本批 generation/任务批次标识。
4. 提交成功后 SQLite 才确认 indexed revision，reader 刷新后再向 UI 宣告可见。
5. 若第 3 步成功、第 4 步前崩溃，启动后核对 commit 与待确认任务，幂等补账或重放。
6. 删除与撤销索引范围也进入同一流程，避免正文、搜索结果与缓存残留。

Tantivy 提供 commit 和 payload 机制，但并未替应用提供与 SQLite 的跨库事务。`prepare_commit` 不能直接当作通用分布式两阶段提交。[IndexWriter](https://docs.rs/tantivy/latest/tantivy/indexer/struct.IndexWriter.html)

跨进程共享索引时，通过明确的 generation 通知触发 reader reload；一次查询固定使用同一个 Searcher 快照，不能在查询中途混用不同 generation 的文档地址。不要在元数据中长期保存 Tantivy 的 segment/doc address。[IndexReader](https://docs.rs/tantivy/latest/tantivy/struct.IndexReader.html)

重建用新 generation 后台构建，完成后切换；旧索引继续提供查询。空间不足、重建失败、切换前崩溃都不应让可用索引被提前清空。

## 6. 进程与语言：保留原生路线，区分职责与生命周期

推荐语言分工：Swift 负责 AppKit/SwiftUI、权限、热键、FSEvents、PDFKit/Vision；Rust 负责 Tantivy、查询规划、纯文本与结构化格式解析、后续实时扫描；C 只保留少量扫描/SIMD 热路径。没有必要把界面改为 Tauri，也不必为了“纯 Swift”自行实现倒排引擎。

UniFFI 可以保留：接口使用批量结果、可取消查询、明确所有权，不逐条跨语言调用。只针对 macOS arm64 时，Rust static library + module map/绑定即可，XCFramework 是可选打包方式，非先决条件。Swift 与 Rust 各自维护的归一化、路径和查询规则必须由共享测试向量约束。

首版建议的职责图：

```text
XSearch.app（菜单栏常驻）
  ├─ AppKit 启动器 / 可固定完整窗口 / SwiftUI 设置
  ├─ QuerySession → NameEngine（后台队列，内存索引）
  │              → ContentReader（后台队列，Tantivy 快照）
  ├─ PreviewController → Text / PDF / Sheet / OCR
  └─ ChangeCoordinator
       ├─ 共用目录规则、FSEvents、对账、FileCatalog
       ├─ 名称索引更新与快照保存
       └─ SQLite 持久任务 → XPC 调度

IndexService（按需启动）
  ├─ 单写者、批量 commit、索引维护
  └─ ExtractionWorker（可重启/终止）
       ├─ Rust 文档解析
       └─ Swift PDFKit / Vision
```

这里 UI 进程不等于主线程：扫描、查询、更新不运行在 MainActor；主线程只做输入与呈现。文件名查询留在进程内可以降低延迟，但“XPC 一定无法满足目标”应改为待测结论。

首版由一个逻辑协调器复用变更规则，避免名称和内容各自演化成两套扫描/排除逻辑。底层按卷或范围建立多个 stream 没有问题。菜单栏应用退出后默认停止后台工作，重启后回放；若确实要求退出应用仍索引，再把协调器部署为可管理的登录 agent。

`SMAppService` 是后台/登录服务管理选择，XPC 是通信机制，二者不是一一对应。应先决定服务是否需要独立于应用存活，再选 bundled XPC service 或 login agent。只需用户级权限，不需要 root daemon。

解析器和唯一索引写者完全放在同一个 helper 进程，虽然保护了 UI，却仍会让坏文件反复杀死整条索引流水线。至少为高风险解析设计可回收 worker；记录租约、失败次数、退避时间和隔离状态。线程上的超时/取消不能保证终止卡死的同步原生解析，进程边界才提供可强制恢复的手段。

## 7. 分区：保留离线卷能力，不按每个用户根目录机械拆索引

v0.3 第 6.3.1 节提出的分区有价值，但应删除“多个独立索引的联合排序分页由 Tantivy 原生自动完成”的含义。它能够提供底层搜索与统计能力，XSearch 仍须实现联合查询协调；pivotsearch 本地代码中的 MultiIndexSearcher 也是应用层实现。

建议区分：

- **Scope 是用户范围**：多个目录、排除规则、OCR 策略，可重叠，但规则优先级确定，同一文件只提取一次。
- **Partition 是物理索引**：首版本机一个分区；后续按外置卷或很大的独立资料库分区。不要每增加一个子目录就增加 writer、reader 和 merge 任务。

单分区中通过 root/scope IDs 和规范化目录条件过滤。删掉一个 scope，并不代表删除仍属于另一个 scope 的文件。目录前缀匹配必须有路径边界，`/Work/A` 不能误匹配 `/Work/Archive`。

多分区需要定义：稳定排序与 tie-breaker、候选补取、分页游标、失败分区状态、相同文件去重、reader generation、取消。不同分区的 BM25 统计不同，分数不能天真直接相加排序；可先按明确的匹配等级和公共业务规则排序，将分区内相关度作为辅助。若需要严格全局 BM25，再实现与验证全局统计方案。

外置卷使用卷身份加相对路径；同名挂载点不代表同一卷。拔盘后保留索引并标“离线”是可选且有用的能力；缓存文本可以预览，原始 PDF/图片没有本地副本时不能显示原貌。原文件打开和拖拽必须禁用或明确提示。

## 8. 预览必须从第一个内容原型开始实现

不要把预览放到 M3 才验证。搜索、提取和高亮必须共享以下契约：

```text
Match
  file_id + revision + query_id
  normalized_range
       ↓ 归一化映射（可一对多或多对一）
  display_text_range
       ↓ 提取来源映射
  SourceAnchor
    Text(line, column)
    PDF(page, page_text_range, optional_bounds)
    DOCX(part, paragraph/table_cell)
    XLSX(sheet, cell/range)
    PPTX(slide, shape/text_range)
    OCR(page/image, box, orientation/transform)
```

Rust UTF-8 字节偏移、Unicode 字符索引、Swift String.Index、AppKit NSRange/UTF-16 不可混用。NFKC、大小写折叠、换行处理都可能改变长度。以 `ﬁ`、组合音标、emoji、全角字符等构造测试；完整保留显示文本，不能只存归一化正文。

PDF 页码只能把人带到一页。字符级高亮需要该页文字层的区间与 PDFKit selection 对应；本机 SDK 确认 PDFPage 提供 character bounds 和 range selection。保存页内原提取字符串的范围，核对原文件 revision 后再映射。断词重建、旋转页、CropBox、多栏需要单独测试。

Office 预览不能全部只叫“正文”：

| 格式 | 首版建议的可兑现能力 | 不应默认承诺 |
|---|---|---|
| 文本/代码 | 行号、命中跳转、复制、可选语法着色 | 所有编辑器均支持同一种行列跳转 |
| DOCX | 结构化提取文本，段落和表格定位 | 与 Word 完全一致的排版或稳定原文件页码 |
| XLSX | 工作表、单元格地址、命中附近的二维表格 | 只显示长串文本便算单元格定位 |
| PPTX | 幻灯片编号、文本块定位 | 任意第三方应用都接受外部幻灯片跳转 |
| PDF | 原页面、页码、选区高亮 | 仅靠全局关键词再次 find 就与索引命中一一对应 |
| 图片/扫描 PDF | 原图上的 OCR 框，识别文本可选复制 | OCR 框一定精确到单个字符 |

文件已变更时提示“索引版本待更新”，重排提取；旧文本不能静默画到新 PDF/图片上。

`⌘↵` 建议定义为“在 XSearch 阅读窗口定位命中”；外部编辑器跳行作为支持列表内的操作。对 Office，“打开默认应用 + 复制关键词”可以作为辅助操作，但写入查找剪贴板不保证每个应用的 `⌘F` 自动使用它。

## 9. 交互：可见模式切换为主，命令为可选捷径

建议首版只保留两个主要模式：**名称、内容**。名称模式同时支持应用与文件启动；应用启动是第一阶段的明确功能，扫描应用 bundle 元数据和别名并用 NSWorkspace 打开，不依赖 Spotlight。

模式栏明确显示当前状态，`⌘1/⌘2` 切换，可选独立的“直接呼出内容搜索”热键。切换时保留查询、范围及各自选择位置。默认呼出名称模式，提供记住上次模式选项，避免某次切换使下一次启动应用时意外扫正文。

命令别名建议用 `name:` / `content:`，可以自动转为可见模式 chip；`in:` 仅表示路径范围。不要首版同时引入 `in 词`、`in:路径`、单引号、`f` 等多套隐式规则。普通输入不强迫用户学习命令。

“全部”模式后置。未来如果需要，用同一个文件行显示名称/正文命中标签，去重后渐进补内容结果；不能简单混合两种不同评分，也不要让结果不断跳动导致误打开。

紧凑面板用于快速打开；内容模式展开双栏，选中即预览；完整窗口用于持续研究资料，支持固定、调整大小、范围筛选。v0.3 新增完整窗口与收藏值得保留，但共享 QuerySession、ResultModel 和 PreviewController，避免两套搜索实现。

建议的交互细节：

- 输入框需要获得键盘焦点；nonactivating panel 指不按普通应用方式激活，不等于完全不接收焦点。关闭后恢复原应用交互。
- 中文输入法有 marked text 时，不把拼音组合当成最终搜索，不拦截候选用的空格、回车、方向键。
- Tab 保留焦点导航；模式切换用明确快捷键。空格只有结果列表获得相应焦点时才是 Quick Look。
- `⌘C` 在文本选区时复制文本；复制路径使用独立快捷键/菜单。不能全局覆盖编辑习惯。
- Esc 先关闭子查找/弹层，再关闭面板；固定完整窗口点击外部不消失。
- 搜索结果默认不先计算每个文件的全部命中数；选中后计算 N，列表可先显示 snippet。按命中数全局排序后置。
- 收藏绑定逻辑文件身份并保留重定位信息，不能仅存路径；删除索引不删除收藏。
- 首版移除快捷移到废纸篓功能，先保证查找、打开、拖出、复制与定位的稳定性。

DocFetcher 的选择即预览、范围控制很适合完整窗口，但其官方 FAQ 也明确说明命中计数与原文件重解析的成本。XSearch 缓存提取文本可避免反复解析，仍应避免对所有候选同步统计所有命中。[DocFetcher FAQ](https://sourceforge.net/p/docfetcher/wiki/FAQ/)

## 10. 提取和 OCR：把“支持格式”改成能力矩阵

### 10.1 文档提取

首版顺序建议为：文本/Markdown/代码 → 文字层 PDF + DOCX → XLSX/PPTX → OCR。每种格式同时交付预览锚点，不先只生成一个长字符串。

DOCX 需要逐项定义正文、表格、页眉页脚、脚注、尾注、文本框、批注、修订的纳入规则；XLSX 明确显示值/公式/隐藏工作表/批注；PPTX 明确备注、表格和形状文字。成熟库与针对性解析结合，比默认全部手写 zip/XML 更可控。

UTF-16 LE/BE、BOM、UTF-8 和 Windows 常见文本编码需要优先覆盖。编码检测存在歧义，要允许按文件/目录覆盖，并显示替换字符和疑似乱码状态。UTType 常提供类型声明，魔数才是另一种证据；两者都不是万能格式判定器。

100MB 的输入上限不能控制解析成本。还要限定解压后字节、条目数、嵌套深度、页数、像素数、抽取文本长度、内存和执行时间。部分处理必须标“部分索引”，不能当完整成功。

归档内部文件具有容器链和虚拟路径，不能直接作为普通磁盘文件打开/拖拽。邮件附件也要建父子关系。iWork 包内预览不一定存在或完整，不能写成已确定支持路线。旧 Office、iWork、OFD/WPS、邮件与嵌套压缩包留作按需求扩展。

DocFetcher 的成熟价值是格式接入和长期处理真实文档的经验。需要旧 Office 等广覆盖时，可以评估基于 POI/PDFBox/Tika 的独立提取 helper，但这会增加运行时、安装体积、签名和内存成本；不应为了“参考 DocFetcher”而首版捆绑 JVM。标准解析结果协议使后期替换引擎可行。

### 10.2 OCR

本机 macOS SDK 验证：`RecognizeTextRequest` 可用性从 macOS 15 起；`RecognizeDocumentsRequest` 和 `NSGlassEffectView` 从 macOS 26 起。原文把前者也归为 macOS 26 新 API，应改正。最低 macOS 26 可以作为产品选择保留，但 arm64 与系统最低版本是两个独立决策。

建议修改固定 OCR 规则：

- 逐页判断文字层质量，混合 PDF 不要整份重复 OCR；保留文字层和 OCR 的来源并去重。
- 分辨率由页面尺寸、目标 DPI、文字尺度和像素预算决定，不能只写“2 倍”。
- 首个 OCR 任务到来或空闲时再预热，避免每次启动常驻加载模型。
- 语言按实际语料配置，并检查 request 支持列表；中文公文、英文编号与繁体文档可需要不同参数。
- 自然语言可尝试纠错；编号、金额、代码不宜不加区别地开启语言纠错。
- 不无条件删英文行尾连字符，也不无条件拼接中文换行；保留原始文本与可追溯的阅读顺序映射。
- 第二候选默认关闭；若开启，必须单独标记候选来源，并在核验/预览中一致呈现，不能从主候选全文核验后又把第二候选结果过滤掉。
- “疑似无文字”和“短边小于 64px”只能是性能策略，不能保证不漏有意义文字；支持用户强制识别。
- 从并发 1 起测，按内存/温度适配；电池状态优先暂停 OCR 和大批量历史任务，轻量名称更新与小文档更新继续。

二维码是独立内容来源，首版可以后置。

## 11. 权限、范围与本地数据

非沙盒分发和完全磁盘访问是不同概念。“没有 FDA 就不能使用”不应成为首启前提。先允许选择可访问目录，遇到受保护范围再解释缺失权限；正式签名 app、XPC helper、子进程的访问链必须在原型阶段验证，不能依赖开发终端已有的权限。

默认建议：名称覆盖应用和常用用户目录，可选扩到整盘；内容仅覆盖用户明确勾选的资料目录；外置盘先选择是否索引，名称与内容分开；网络盘默认不全文索引。iCloud/File Provider 的未下载文件应标记为仅元数据，不因后台全文扫描悄悄下载大量云文件。

设置页应能解释“为什么搜不到”：未选择范围、排除、无权限、仅云端、类型不支持、部分提取、失败、待更新、卷离线。索引进度展示已发现/已完成/待处理/失败，不为了准确百分比先完整扫描两遍。

源文件删除、取消范围、清理缓存和卸载时，要说明哪些提取文本会清除。文本缓存可能含敏感内容，保持用户私有权限、限制日志，不将正文和搜索词写入普通诊断日志。可重建索引和不可重建的收藏/设置分别备份管理。

原文“完全不联网”与 Sparkle 自动更新不一致，建议改为“文件内容和查询本地处理；更新检查可独立关闭，不上传文件或查询”。

## 12. 性能指标应换成可复现的验收方法

oil-find README 的 85 万文件数据来自特定 M5、24GB、特定排除范围和 CLI 测量，不能直接转为整个 XSearch 的 60MB 或所有 M 系列都适用的保证。DocFetcher 的约 200 文件/分钟与 pivotsearch 的吞吐量同样不宜横向直接比较。[oil-find 性能条件](https://github.com/oil-oil/oil-find)

v0.3 新增“Office ≥300 文件/秒、PDF ≥30 文件/秒”缺少文件大小、页数和内容复杂度；应删除硬性承诺。一个两页 PDF 和一个 800 页扫描 PDF 没有可比性。

建议先设体验目标，再由 M0 在目标机器上校准：

| 指标 | 初始目标或记录方法 |
|---|---|
| 常驻状态热键到输入框可输入 | P95 <50ms；单独记录冷启动 |
| 名称输入完成到首屏呈现 | P95 <80ms；引擎耗时单独记录 |
| 已索引普通内容查询到首屏已核验结果 | P95 <200ms，限定公布的语料和查询集 |
| 单字、高频词、否定/正则等重查询 | 单独测试可取消、渐进结果与完整性，不混入普通查询平均值 |
| 选中文件到首个高亮可见 | 普通已缓存文档 P95 <200ms；超大文档单列 |
| 小型非 OCR 文本保存到可搜索 | 在队列空闲、已获权限的条件下以 <3 秒为初始目标 |
| OCR 新鲜度 | 页数/队列/电源条件下的完成时间，显示进度 |
| 首次扫描 | 发现首批可搜结果、完整扫描时间、磁盘缓存冷热分别记录 |
| 内存 | NameEngine、UI、reader cache、writer、解析/OCR 分进程记录 idle/peak 与 memory pressure |
| 索引体积 | 元数据、倒排、存储文本、位置映射分别除以提取文本体积，并记录真实磁盘占用 |
| 功耗 | 空闲唤醒、CPU、后台任务暂停恢复、低电量与热压力 |

以上为建议目标，不是本次实测成绩。最少包含 10 万/85 万/百万级名称数据和按提取文本量分级的内容集；查询集覆盖中文一二三字、英文中间子串、数字片段、拼音、标点、路径过滤、高频词、多条件和连续输入。

## 13. 更合理的实施顺序

| 阶段 | 核心交付 | 通过条件 |
|---|---|---|
| M0 架构验证 | 名称基准；Tantivy 字面召回原型；FTS5 作为小规模对照；Tantivy stored fields；UTF-8/UTF-16 与 PDF 高亮；签名后的权限与 XPC 验证 | 关键语义正确；可复现耗时/内存/体积；决定是否需要独立文本存储 |
| M1 名称与启动 | NSPanel、应用启动、扫描、快照、FSEvents、名称搜索、拼音、基础过滤、打开/访达定位 | 进程重启、改名/移动/删除、事件回放正常；主线程无扫描阻塞 |
| M2 内容最小闭环 | 文本 + 文字层 PDF + DOCX；任务持久化；字面召回/核验；双栏预览、高亮、命中跳转；范围与错误状态 | 从新增文件到搜索定位全流程正确；崩溃重放不损坏已可用索引 |
| M3 日常资料体验 | XLSX/PPTX 结构定位、可固定完整窗口、收藏、多条件筛选、格式覆盖补齐 | 常用真实文档可稳定定位；不把所有 Office 当纯文本 |
| M4 OCR 与按需扫描 | 截图/扫描页 OCR、混合 PDF、坐标映射、明确触发的目录实时扫描 | OCR 质量与耗时有样本报告；可暂停/恢复/取消 |
| M5 扩展与发布 | 外置卷离线内容、按需分区、旧格式/归档/邮件按优先级；升级回滚、DMG、公证、更新 | 迁移与重建可恢复；性能与准确性回归通过 |

CLI/基准工具前置到 M0，而非 M4：它是检索语义、数据规模和故障恢复的验证入口。签名权限验证前置，正式发布包装后置。装饰效果和全部模式不进入关键路径。

M0 需要用户确认后才开始；本次只是定义它，不创建应用工程或进行实现。

最小正确性集必须包括：中文/英文/数字子串与暴力扫描对照、NOT/OR/AND、多块边界、Unicode 映射、输入法组合、原子保存与目录改名、同名卷/离线卷、提取中变化、无权限与断网、各持久化步骤中断、reader 重载、文件损坏、磁盘写满、重建失败。

实时扫描建议明确区分“已索引内容”和“扫描当前文件夹”。普通文本可用 ripgrep 系列库；PDF/Office 不会因为交给 grep 就自动可搜。结果显示扫描范围、进度与是否完成，遵守同样的排除和编码规则；未索引目录不应在每次按键时悄悄启动全目录深扫。

## 15. 建议用户确认的决策

推荐整体采用以下组合：

1. 原生 Swift/AppKit + Rust/Tantivy，保留少量 C 热路径；最低 macOS 26 按当前文档执行。
2. 文件名与内容分开检索，名称包含应用启动；可见切换为主，“全部”后置。
3. 字面子串优先、无停用词召回；完整性声明限定到成功提取文本。
4. Tantivy 自带正文存储先行，自研 pack 和每目录独立分区暂缓。
5. 名称引擎、内容索引、预览和恢复协议通过 M0 验证后，再开始正式模块建设。
6. 首版聚焦文本、PDF、DOCX/XLSX/PPTX 与可靠定位；OCR 紧随，特殊格式按实际文件占比排期。

尚需产品偏好确认的是：是否坚持 macOS 26 起、是否日常大量使用 OFD/WPS/旧 Office、是否要求“完全退出 XSearch 后仍持续索引”。这些会影响范围和部署方式；其余常规工程细节可以在已确认方向内继续推进，无需逐项审批。
