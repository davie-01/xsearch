## 1. 产品定位与承诺

XSearch 是一个常驻菜单栏、按快捷键呼出的启动器，提供三项能力：

1. **应用启动**：不依赖 Spotlight，自己扫描应用包。
2. **文件名搜索**：自建内存索引，输入即出结果。
3. **文件内容搜索**：自建全文索引，预览时能定位并高亮命中处。

**“精准”的明确定义**：在用户设置的内容索引范围内，对**已成功、完整提取**的文本，按第 8.2 节的归一化规则做字面子串检索，结果不会因为分词、候选截断或分页而漏掉。以下情况不在此承诺内，但会分别显示状态，不会显示成“没有结果”：

- 未纳入索引范围；
- 被排除；
- 没有访问权限；
- 文件只在云端；
- 类型不支持；
- 只提取了一部分；
- 提取失败；
- 文件已变化、索引待更新；
- 磁盘离线；
- OCR 识别不确定（OCR 上线后）。

**数据原则**：文件内容和搜索词只在本机处理，不上传。唯一的联网行为是检查更新，可以在设置里关闭。用户主动启用 MCP 接口并授权外部客户端后，交给该客户端的结果不在这一保证范围内（第 15 节）。

## 2. 已确认的决策

| 编号 | 决策 |
|---|---|
| D1 | 只支持 macOS 26 及以上、arm64 |
| D2 | 界面用原生 Swift/AppKit；内容引擎用 Rust/Tantivy；扫描、匹配等热路径用少量 C/NEON |
| D3 | 文件名和内容分开检索。主要切换方式是可见的模式栏 **[名称] [内容]**；“全部”模式以后再做 |
| D4 | 命令前缀：`in 词` 进入内容模式；`dir:路径` 限定目录范围。通配符（`*.doc`）、正则等语法功能后置，并在设置里分别提供开关（第 12 节） |
| D5 | 索引范围在设置中**分别配置文件名和内容**：可以选整盘，也可以选一个或多个文件夹，并支持排除规则（第 6 节） |
| D6 | 不需要在完全退出 XSearch 后继续建索引。后台服务的生命周期跟随主应用；下次启动时，用 FSEvents 的历史记录补齐退出期间的变化。主应用可以设为开机自动启动 |
| D7 | 旧版 .doc 文件多，所以 **.doc 和 .docx 一起进入首个内容版本（M2）**；OFD 放在 M3；WPS 放在 M4 |
| D8 | 图片和扫描版 PDF 的 OCR 放在**最后一个功能阶段（M6）**。M2 先预留三项接口（第 14 节），保证以后接入时不需要返工 |
| D9 | 首版正文直接存进 Tantivy 的 stored fields，不自己实现文本存储。**每个文件的 Tantivy 文档各自保存自己的正文和锚点**；相同内容的副本只是“复用提取结果、避免重复解析”，不做磁盘上的物理共享（第 10 节）。只有 M0 实测出瓶颈时，才引入单独的存储后端或物理去重 |
| D10 | 默认呼出快捷键为 **⌥Space（Option+Space）**，可在设置中修改 |
| D11 | 首次启动时，内容索引范围**只推荐“下载”目录**（`~/Downloads`），其他目录由用户之后在设置中自行添加 |
| D12 | 内容归一化以 Rust 中固定版本的 Unicode 数据为唯一实现，Swift 通过 C ABI 获取文本与映射。不能分别依赖 Foundation 的折叠/分解结果；M0 已验证二者存在差异。当前规则数据版本为 Unicode 17.0.0 |
| D13 | **去掉拼音搜索**：名称模式只按文件名中的字面字符匹配。拼音首字母和英文缩写难以区分（例如 `sj` 可能是“数据”，也可能是英文），实际使用中用处不大。不建拼音别名区，排序中没有拼音档位，设置中没有拼音开关 |

## 4. 技术栈

| 层 | 选型 |
|---|---|
| 工具链 | Xcode 26、Swift 6.2（严格并发检查）、Rust stable（aarch64-apple-darwin） |
| 工程 | XcodeGen 生成工程；Rust 编成静态库，通过 UniFFI 生成 Swift 绑定（XCFramework 只是可选的打包方式） |
| UI | AppKit：NSPanel 启动器、结果列表、预览、完整窗口；SwiftUI：设置页、引导页；视觉效果用 `NSGlassEffectView`（macOS 26） |
| 文件名引擎 | Swift + C（NEON） |
| 内容引擎 | Rust：Tantivy、自定义 n-gram 分词器、查询规划器（AST）、结构化解析器 |
| 系统能力 | PDFKit（PDF 文字层和高亮）、NSAttributedString / `textutil`（.doc/.rtf）、Vision（OCR，M6）、UTType |
| 元数据 | SQLite（WAL 模式）：文件目录、任务、状态；个人数据单独放在 user.sqlite |
| 进程通信 | XPC Service，打包在应用内部，生命周期跟随主应用 |
| 分发 | Developer ID 签名、公证、DMG、Sparkle；不开沙盒 |

Swift 和 Rust 各自实现的归一化、路径、查询规则，用同一套共享测试向量约束，保证两边结果一致。

## 5. 进程架构

```
XSearch.app（菜单栏常驻；可设为开机启动）
 ├─ AppKit：启动器面板 / 完整窗口 / SwiftUI 设置页（主线程只做输入和呈现）
 ├─ QuerySession ─┬─ NameEngine（后台队列，内存索引）
 │                └─ ContentReader（后台队列，固定在一个 Tantivy Searcher 快照上）
 ├─ PreviewController ── Text / PDF / Doc / Sheet / Slide /（M6）OCR
 └─ ChangeCoordinator（名称和内容共用同一套范围和排除规则）
      ├─ ScopeManager（第 6 节）
      ├─ FileCatalog（SQLite：file_id、路径、身份、版本、范围标记、状态）
      ├─ FSEvents（按卷建立 stream，lastEventId 持久化）+ 定时对账
      ├─ 更新名称索引并保存快照
      └─ 内容任务写入 SQLite ──XPC──▶ IndexService

IndexService.xpc（打包在应用内，主应用退出时随之退出）
 ├─ 唯一的 Tantivy 写入者：批量 commit，commit payload 中记录 index_instance_id 和 commit_batch_id
 └─ 调度 ExtractionWorker.xpc（可以被回收、被强制终止）
      ├─ Rust 解析器：txt/代码/docx/xlsx/xls/pptx/ofd…
      ├─ Swift 提取器：PDFKit、NSAttributedString(.doc)
      └─（M6）Vision OCR
```

设计要点：
- **解析放在独立的 worker 进程**（M2 实现：打包在应用内的辅助可执行文件 `xs-extract`，通过标准输入输出按长度分帧收发请求，而不是 XPC Service。理由：可以直接按 pid 强杀、能在 `swift test` 中做超时和崩溃注入；应用不开沙盒，辅助进程读文件的权限归属与 XPC 子进程相同，M0 的“主程序 → XPC → 子进程”链路测试已覆盖子进程读文件）。遇到坏文件导致卡死或崩溃时，可以强制终止 worker；记录失败次数，按退避策略重试，多次失败后隔离该文件，不会拖垮索引写入。
- **UI 进程不等于主线程**。扫描、查询、更新都在后台队列执行。
- 文件名查询放在 UI 进程内，用来降低延迟。M0-B 实测稳态 XPC 往返 P95 约 25–52 µs（0–64 KB），首次连接冷启动约 16 ms，因此 IndexService 在应用启动时预热。

## 6. 索引范围（Scope）

### 6.1 配置模型

文件名范围和内容范围**分别配置**，结构相同：

```
Scope
  roots:     [整盘 "/" | 文件夹路径 | 外置卷(卷UUID)]，可以多选
  excludes:  [文件夹路径 | glob 规则（如 **/node_modules/**）| 扩展名]
  options:   包含隐藏文件 / 包含应用包内部 / 包含 ~/Library / 是否跟随外置盘
内容范围额外的配置：
  types:     要提取的文件类型（按能力矩阵勾选）
  limits:    单文件大小上限、页数上限、解压后大小上限
  ocr:       （M6）对哪些子范围启用 OCR
```

默认值：
- **文件名范围**：整盘，排除 `node_modules`、`.git`、应用包内部、`~/Library`、系统目录。效果和 Everything 一样。
- **内容范围**：首次启动时**只推荐 `~/Downloads`**（用户可以在引导页取消），其他目录由用户之后在设置中自行添加。网络盘默认不建内容索引；iCloud 中没下载到本地的文件只索引文件名，不会为了建全文索引去下载。

### 6.2 实现

- 用一个 FileCatalog 记录**两个范围的并集**，每个条目带有 `in_name` 和 `in_content` 两个标记。只扫描一遍，同一个文件只提取一次。
- 修改范围时计算差异：新增的部分进入扫描队列；移出的部分**分别按名称和内容两套规则处理**：
  - **名称**：只要还有任意一个名称范围覆盖这个文件，就保留它的名称条目，否则删除；
  - **内容**：只要还有任意一个**内容范围**覆盖这个文件，就保留它的内容索引，否则删除（op_seq 加 1，并进入删除任务）。**只被名称范围覆盖的文件，不能保留内容索引**；
  - 内容索引被删除时，这个文件的正文、锚点、页级状态随它的 Tantivy 文档一起删除。因为首版不做物理共享（D9），**不需要引用计数**。
  - 要区分两层：**查询层删除**在删除操作 commit 之后立即生效，删掉的文档不会再出现在任何新的查询结果里；**磁盘空间回收**是另一回事，要等段合并以及无用索引文件的清理（garbage collect）完成后才发生，并且还要等仍持有旧 Searcher 的查询结束。所以**不承诺删除后正文立即从磁盘上消失**。
  - 对策：删除范围或手动“清理”时，主动触发段合并和无用文件回收，并在设置页显示“待回收空间”；用户要求彻底清除时，提供“重建内容索引”的选项，按 9.3 节第 7 步重建后删除旧实例目录。
- **范围调整、提取配置修改、提取器升级都写入操作日志**（9.2 节的 `op_journal`），并给受影响的文件生成新的 op_seq 和任务。这些变化不一定伴随 FSEvents，不能只依赖文件系统事件。
- 路径前缀匹配必须卡在路径分隔符上：`/Work/A` 不能匹配到 `/Work/Archive`。
- 设置页**按范围显示索引占用的大小和文件数**（参考 Cling），方便用户裁掉不需要的目录。
- 设置页里有一个“**为什么搜不到**”的诊断功能：输入一个路径，显示它属于哪个范围、被哪条规则排除、权限情况、提取状态、最近一次索引时间。

### 6.3 物理分区（Partition）

- 首版只有**一个本机内容分区**，用 scope 字段过滤。
- 外置卷各自建独立分区（以卷 UUID 命名），拔掉后索引仍保留，可以继续搜（结果标为“离线”，可以预览缓存的文本，不能打开原文件）。这项能力放在 M4。
- 跨分区查询由应用层合并：先按统一的匹配等级排序，再用分区内的相关度辅助排序；每个分区的失败状态单独显示。不做全局 BM25。

## 7. 文件名引擎（NameEngine）

- **数据**：列式数组 `nameOff / parent / size / mtime / flags / kind`，所有文件名的 UTF-8 字节拼成一块。持久化文件先映射读取、再复制进可变的内存索引（和 oil-find 一样），不设计可变的 mmap 文件。
- **扫描**：C 实现，用 getattrlistbulk 按子树多线程扫描；扫描完成先发布第一批结果，再在后台补全。
- **布局（参考 fsearch，M0-B 已定）**：条目按“目录块、深度优先”排列，每个目录的整个子树是一段连续区间，`dir:` 过滤就变成一次区间约束；名称做驻留，查询时只给不同的名称打分。增量修改采用“基础快照 + 增量覆盖层”，在后台按条目数或时间合并，合并完成后原子替换快照；M0-B 中 1% 增量已使查询明显变慢，所以合并阈值要远低于 1%，M1 用真实数据确定。字符类位图预筛在 M0-B 中没有稳定收益，不采用。约束如下：
  - “目录子树是一段连续区间”只对基础快照成立。新增、移动、删除的条目在增量层里，`dir:` 查询必须**同时查增量层，并处理覆盖关系**：已删除、已移走的快照条目要屏蔽，移入的新条目要补上。否则会漏掉新文件，或者显示旧路径。
  - 同名文件可以共享“名称匹配得分”，但修改时间、路径深度、使用频率等最终排序因素，仍然按每个文件单独计算。
  - 驻留在名称重复多时速度和内存都明显改善，名称全不同时只多约 5% 内存。真实磁盘的不同名称比例在 M1 扫描时记录，不作为设计前提。
- **执行策略**：多个 AND 条件按代价排序（先算最便宜的）；对于很短的查询，在索引查找和 NEON 线性扫描之间按代价自动选择（参考 MacEverything）。
- **收窄**：“新查询是旧查询的继续输入”**不是**充分条件。例如 `-合同` 改成 `-合同书`，结果可能变多；`合同` 改成 `合同 | 发票`，结果集会扩大。规则改为：**只有查询规划器能证明“新查询的结果一定是旧查询结果的子集”时**，才在上次的完整结果集（不是只看屏幕上显示的几条）上继续筛选，否则重新执行。另外，索引版本、选项、过滤条件也必须都没变。
  - 首版只对白名单启用：所有子句都是正向字面子串，新查询只是在某个子句末尾追加字符，或者新增一个正向 AND 子句。
  - **M0 补充**：还必须比较归一化后的名称键。`cafe` 追加组合重音变成 `cafe\u0301` 时，NFC 会把末尾改成 `é`，新结果不一定是旧结果的子集，必须重新执行。完整旧结果集、索引版本、模式与范围共同构成复用条件。
  - 涉及 NOT、OR、通配符、正则、语法开关变化、模式切换时，一律重新执行。
- **应用启动**：扫描 `/Applications`、`/System/Applications`、`~/Applications`，读取 bundle 名和本地化名，用 NSWorkspace 打开。应用在名称模式里优先排序。
- **Unicode**：文件名统一转成 NFC 再比较，大小写不敏感。
- **不支持拼音搜索**（D13）：输入的字母只按文件名中的字面字符匹配。
- **排序**：完全相同 > 前缀 > 单词边界 > 子串 > 模糊；再按使用频率、修改时间、路径深度加权。

## 8. 内容引擎（Rust）

### 8.1 文本的三种形态

| 文本 | 说明 | 存放位置 |
|---|---|---|
| display_text | 提取出的原始文本，完整保留 | Tantivy stored field |
| search_text | 按 8.2 节“XSearch 自定义归一化”处理后的文本，用来生成 trigram，也是宽松模式的核验对象 | 每次按需生成（M0 实测生成成本，必要时缓存） |
| norm_map | search_text 和 display_text 之间的偏移映射 | 随 search_text 一起生成 |
| anchors | display_text 区间 → 原文件位置（第 11 节） | Tantivy stored bytes |

### 8.2 归一化规则

**索引用的归一化必须“保持子串关系”**：如果 s 是原文 t 的子串，那么 norm(s) 一定是 norm(t) 的子串。只有满足这一点，任何查询模式（包括严格模式）都能先用 norm(查询) 从索引里召回到完整的候选集，再在原文上核验，不会漏。

- **索引归一化 norm（按码点逐个独立映射，不做跨字符的组合）**：每个码点做兼容分解（相当于对单个码点做 NFKD），再做大小写折叠，全角转半角；所有空白字符映射成空格，连续空白合并成一个（合并操作同样保持子串关系）。**不使用整串 NFC/NFKC**：它们会把相邻字符组合到一起（例如 `e` + 组合重音会变成 `é`），破坏子串关系，导致严格模式漏召回。保留标点和符号。
- 这套规则称为 **XSearch 自定义归一化**。它不等于对整串做 NFKD（不做组合标记的规范排序），**不承诺所有 Unicode 规范等价的字符串都能互相匹配**，只承诺第 1 节定义的字面子串召回不漏。
- **M0 实现约束**：固定 `unicode-normalization 0.1.25` 的 Unicode 17.0.0 分解表和同版本 `CaseFolding.txt` 的 C/F 全折叠规则；Swift 复用 Rust C ABI，不自行使用系统折叠/分解。持久化 `norm_ver`，不兼容版本在打开索引时拒绝查询并要求重建。M0 的 54,408 组跨边界向量验证了 JSON/C ABI 传输与映射一致性，原 Foundation 独立实现出现 99 组差异。
- **三种互斥的匹配模式**，共用同一个宽松索引做召回：

| 模式 | 核验对象和规则 | 命中区间属于 |
|---|---|---|
| 宽松（默认） | 查询和原文都做完整的 norm（兼容映射 + 大小写折叠 + 空白合并） | search_text，经 norm_map 换算到 display_text |
| 区分大小写 | 保留兼容映射和空白合并，**只关闭大小写折叠**（norm_cs） | norm_cs 文本，经它自己的映射换算到 display_text |
| 严格原文 | display_text 的原始码点序列直接比较 | **直接就是 display_text 区间**，不再经过映射 |

- 三种模式都满足“宽松召回结果是核验结果的超集”：norm_cs 和恒等映射保持子串关系，在它们之上再做的大小写折叠也是按码点映射。每种模式都要单独做“召回 ⊇ 核验”的对照测试。
- **反例（说明为什么不能用整串 NFKC）**：原文 `cafe\u0301` 包含子串 `cafe`，但整串做 NFKC 之后变成 `café`，字节 trigram 里就没有查询需要的 `afe` 了，候选阶段直接漏掉，核验阶段无法补救。改为按码点映射后，原文保持 `cafe` + `\u0301`，召回正常。这个例子列为必过测试。
- 用共享测试向量验证子串关系：连字 `ﬁ`、组合字符、全角字符、韩文字母、emoji、各种空白字符。另外用随机生成的子串做对照测试，检查是否满足 norm(s) ⊆ norm(t)。规则层面已经做过 20,000 组抽样检查，没有发现反例；Swift 和 Rust 的实际实现仍要通过同一套测试。
- 万一 M0 发现某个映射无法保持子串关系，严格模式就退回到在所选范围内扫描原始 display_text 的方式，并显示扫描进度。

### 8.3 字面召回

**首选方案：UTF-8 字节 trigram**（参考 fsearch、Google Code Search）。把 search_text 编码成 UTF-8，对每个字节位置取连续 3 个字节作为一个 trigram（24 位整数），每个文档只记录“包含哪些 trigram”，不记录位置。在 Tantivy 中实现为多值 u64 字段 `tri`（只建索引，记录选项为 Basic），文档内去重。

- **字节长度**：基本区的常用汉字通常占 3 个字节，所以搜 1 个这类汉字 = 查 1 个 trigram，搜 2 个汉字 = 查 4 个 trigram 求交集。扩展区汉字（如 `𠀀`）、emoji 占 4 个字节；`α` 等占 2 个字节。注意：长度按**归一化之后**计算，例如 `é` 归一化后分解成 `e` + 组合重音，占 3 个字节。**召回路径按“归一化之后，每个查询子句的 UTF-8 字节长度”来选择**，不按字符种类判断。
- **文件末尾特殊项（参考 fsearch 源码 `index_grams`）**：每个文档额外记录一个“最后两个字节”的特殊项。XSearch 用第 25 位作为标记位，和普通 trigram 区分开，不像 fsearch 那样用 0 字节补位，因此不会和含 NUL 字节的真实 trigram 混淆。这样，出现在文件最末尾的 2 字节子串也能被召回。
- **按查询子句的字节长度选择召回路径**：

| 子句的字节长度 | 召回方式 | 是否完整 |
|---|---|---|
| ≥ 3 | 子句所有 trigram 的交集 | 完整 |
| 2（如 `AI`、`IP`、`α`） | 以这两个字节开头的所有 trigram（Tantivy 对 `tri` 做 `[xy00, xyFF]` 区间查询，最多 256 个词项的并集），再并上“末尾特殊项 = xy” | 完整 |
| 1 | 无法通过索引缩小范围，候选为“其他条件过滤后的全部文档” | 完整，但代价高 |

   2 字节的“前缀区间召回”和“在范围内扫描”两种做法，在 M0 中对比执行成本，**不预先认定 `AI`、`IP`、编号片段这类短查询没有意义**。
- **布尔组合的召回规则**：
  - `合同 AI`（AND）：用代价最小的子句（如“合同”的 trigram 交集）确定候选，其余子句（包括短子句 `AI`）在核验阶段检查，结果完整。
  - `合同 | AI`（OR）：**候选必须取每个子句召回结果的并集**，不能只用“合同”的候选，否则会漏掉只包含 AI 的文件。只要某个 OR 分支是 1 字节子句，整个 OR 的候选就退化为“过滤后的全部文档”。
  - `-甲`（NOT）：不参与召回，只在核验阶段执行。**只有 NOT 的查询**（如 `-合同`），候选为“其他条件过滤后的全部文档”。
- **短查询扫描的对象是已经提取、存储下来的正文**（display_text），所以 PDF、DOC 等格式也能参与。**这是 M2 的内容查询能力**，和 8.7 节 M4 的“直接扫描原文件”是两套实现。扫描遵守 8.4 节的工作量预算、渐进返回和取消机制。

**可选优化：布隆预筛（参考 fsearch）**。不是内容引擎的必需部分，M0 评估后再决定是否启用：
- 每个文档存一个“5 字节子串布隆过滤器”，用来在读取正文之前排除“trigram 都在、但只是分散出现”的假阳性。
- **它必须能低成本地单独读取**。Tantivy 的 stored fields 按压缩块存储，读一个文档要解压它所在的整块；如果过滤器和正文放在同一个 stored document 里，读过滤器时可能已经把正文解压了，收益会明显缩水。所以过滤器放在 bytes 类型的 fast field，或其他独立布局中，由 M0 决定。
- 字面子句不足 5 个字节时，这个子句跳过布隆预筛。
- **布隆预筛必须遵守查询的布尔逻辑**：AND 的各分支可以分别检查；OR 只要任意一个分支通过就放行，不能把 OR 两侧的探针放在一起求交；NOT 分支不参与预筛。
- 过滤器和正文使用同一套归一化规则、同一个版本号；**过滤器缺失或版本不一致时一律放行**，不能据此排除文件。
- M0 必须先测“不开布隆”的基线，再分别测量：索引体积、过滤器读取成本、实际解压的正文量、端到端延迟。

**备选方案：字符 n-gram**（原 v0.4 方案：单字、双字、三字分别建字段）。M0 用同一份语料，和字节 trigram 对比召回正确性、索引体积、查询延迟，再选定一种。

候选文件再进入**核验**：读取 display_text，生成 search_text，用同一棵查询 AST 精确匹配，得到真实的命中区间。

查询语义：
- `甲 乙`：同一个文件里同时包含两个子串；
- `"甲 乙"`：连续短语；
- `甲 | 乙`：或；
- `-甲`：排除。

**排除（NOT）必须在核验阶段执行**，不能直接从候选里减掉“可能包含排除词”的 gram 结果，否则会误删真实结果。

可选字段 `word`（词典分词）只用来给排序加分，不参与召回。

### 8.4 核验的性能约束

- 目录、类型、时间、大小等条件在候选阶段就先收窄。
- 候选分批核验，首屏只生成必要的片段；文件的全部命中数等用户选中它之后再计算。
- 核验掉假阳性后，继续补取候选，**不能只截前 N 个候选**。
- 查询带有 ID 和取消令牌；用户继续输入后，旧查询立即取消。
- 有工作量预算：预算用完时，标记“仍在搜索”或“结果不完整”，不能把它当成“没有结果”。
- 单字、高频词、正则这类重查询，单独测试它们的渐进返回和完整性。

### 8.5 Schema

| 字段 | 类型 |
|---|---|
| `file_id` | u64，indexed + fast（按此删除和更新） |
| `revision` / `extractor_ver` | u64，stored |
| `norm_ver` | u32，stored，归一化规则版本 |
| `scope_ids` | 多值 u64，indexed |
| `dir_path` | raw string，带分隔符边界的前缀查询 |
| `name` | 文本（n-gram），文件名命中时加分 |
| `tri` | 多值 u64，UTF-8 字节 trigram + 带标记位的末尾特殊项（备选方案为 `g1/g2/g3`），见 8.3 |
| `bloom5` | 可选，默认不建（M0-B：真实语料只减少约 3% 实际解压量，体积增加约 28%）。启用时用 bytes fast field 或独立布局，必须能脱离正文单独读取；带归一化版本号 |
| `extract_key` | bytes，indexed + stored。提取缓存键（见第 10 节），用来查找已有的相同提取结果 |
| `applied_seq` | u64 fast，本文档对应的 op_seq |
| `word` | 文本，可选，只用于排序加分 |
| `ext / kind / source` | raw string（source 取值：text / ocr） |
| `size / mtime` | i64 fast |
| `display_text` | stored（zstd，16 KB 块，启用 doc store 块缓存） |
| `anchors` | stored bytes |
| `extract_state` | 完整 / 部分 / 等待 OCR |

### 8.6 排序

先按匹配等级（短语完整命中 > 全部词命中）分档，再用 BM25、文件名命中、最近修改时间、使用频率加权。邻近查询（`"甲 乙"~N`）后置到 M3，届时先明确距离按 Unicode 字符计数、是否要求顺序、能否跨段落。

### 8.7 实时扫描（M4）

显式触发（在结果页点“扫描此目录”，或者 `dir:` 指向没有内容索引的目录时给出提示），**不会在每次按键时自动启动**。只支持文本类文件（基于 ripgrep 的 grep-searcher），遵守相同的排除规则和编码规则，显示扫描范围、进度，以及是否已经扫完。

## 9. 增量更新与一致性

### 9.1 文件身份与版本

- 文件身份 `file_id` 是逻辑 ID，由卷 UUID、fsid/inode、创建时间、当前路径共同判断。要处理三种情况：inode 被复用、原子保存后 inode 改变、硬链接。
- 三种版本：
  - `revision`：内容版本，取纳秒级 mtime、size，加上事件脏标记；
  - `extractor_ver`：提取器或归一化规则升级时变化，变化后只重排受影响类型的文件；
  - `op_seq`：每个文件的操作序号（9.3 节）；
  - `index_instance_id`：一份完整 Tantivy 索引的实例标识，全量重建时产生新实例；
  - `commit_batch_id`：同一个实例内，每次 commit 的批次号。
  - 原来的 `generation` 同时承担“实例”和“批次”两种含义，容易让恢复代码产生歧义，现在拆成上面两个。
- FSEvents 已经报告变化的文件，即使 mtime 和 size 恰好没变，也要重新检查。

### 9.2 事件处理

- 先启动 watcher、记下当前的事件水位，再开始首次扫描；扫描完成后回放扫描期间发生的事件。
- **事件先写日志，再推进游标**：FSEvents 回调收到的原始变化，先追加写入 SQLite 的 `op_journal` 表（带自增序号 jseq），写入成功后，才推进持久化的 FSEvents 事件 ID。
- **`op_journal` 不只记录文件系统事件**，也记录范围调整、提取配置修改、提取器升级、用户手动重建等操作。这些操作不一定伴随 FSEvents，同样按 jseq 排序、可以回放。
- **名称和内容各自维护处理水位**：`name_applied_jseq`（名称索引的变化已经持久化，即快照或增量日志已经落盘），`content_enqueued_jseq`（对应的内容任务已经写入任务表）。两个水位分别推进；崩溃后各自从自己的水位开始重放日志。
- **日志清理**：只删除 jseq 小于两个水位中较小值的记录，也就是说，没被所有消费者处理完的事件不能删。
- 日志的回放是幂等的：对同一个路径重复执行“重新检查（stat）→ 比对 → 更新”，结果不会出错。
- 任务优先级：应用索引最先建好（参考 Fastlight）；**用户正在搜索的 `dir:` 目录优先建索引**（参考 fsearch）；然后是最近修改的文件；最后是历史文件。
- **任务身份为 `file_id + op_seq + task_type`**，按它去重。凡是会影响提取结果或索引字段的变化，都必须让 op_seq 加 1、生成新任务：文件内容变化、删除、重新纳入或移出内容范围、提取配置修改、提取器升级、路径或所属范围变化（`dir_path`、`scope_ids` 会变）。所以，即使文件字节没变、只升级了提取器，新任务也不会被旧任务挡住。
- 文件在处理过程中又变了，就会有一个更大 op_seq 的新任务，旧任务的结果在提交时会被丢弃。
- 收到 `MustScanSubDirs` 时重扫对应子树；收到事件丢失、`RootChanged`、`EventIdsWrapped` 时，扩大到整个受影响的监控范围重扫；卷挂载和卸载单独处理。
- 对账失败或没有权限时，**不能当成目录为空**，也不能因此删除旧索引。
- 网络盘：监听挂载事件，并定时对账（默认 30 分钟），在界面上显示最近一次成功对账的时间。
- **M1 实现的对账规则**（事件只用来决定“去列哪个目录”，判断全部来自磁盘与目录的比较）：
  - 同名同类型视为同一文件；文件在原路径换了 inode 是原子保存，保留 file_id；**目录在原路径换了 inode 是另一个目录**（删除重建，或移走后原地新建），旧行按消失处理。
  - 消失的名称与新出现的名称 dev+inode 相同、类型相同，视为改名/移动，保留 file_id，目录子树随父 ID 跟随；移动的目录在新位置递归对账一次。
  - 消失的条目用 `fsgetpath` 查它现在的位置；仍在范围内就去对账新位置的父目录，避免把移动当成删除 + 新增。
  - 事件路径中途有目录在本批被改名时，先对账最近的已知祖先，识别移动后再重新解析；按此迭代到没有新目录可列。
  - 同一批次连续失败两次时跳过该批，并对全部范围做一次全量对账，不让单个批次卡住流水线。

### 9.3 提交协议

0. **每个文件维护一个操作序号 `op_seq`**：在 FileCatalog 中持久化，并且单调递增。内容变化、删除、移出内容范围、提取器版本升级，都会让 op_seq 加 1。每个任务都带上它创建时的 op_seq。
1. SQLite 写入待处理任务：file_id、op_seq、任务类型（索引 / 删除）、状态、租约 ID、租约到期时间。
2. worker 提取文本，提取前后各核对一次文件版本；如果中途变了，就丢弃本次结果，重新排队。这一步只是为了尽早放弃无用功，**正确性不靠它，靠第 3 步的序号检查**。
3. **IndexService 写入前做两项检查**：任务的租约仍然有效；任务的 op_seq **等于**该文件当前最新的 op_seq（从 FileCatalog 读取），**并且**大于该文件的“写入端已应用序号”（见下文）。不满足就丢弃结果。这样，已经完成但返回晚了的旧任务，不会覆盖新结果，也不会让已经删除的文件“复活”。检查通过后，按 file_id 幂等更新文档，正文、anchors、trigram 和 `applied_seq` 一起写入。删除也按同样的规则排序：删除会让 op_seq 加 1，所以比它早的索引任务在检查时都会因为序号不等于当前值而被丢弃，已删除的文件不会被迟到的旧任务写回来。commit payload 中写入 `index_instance_id`、`commit_batch_id` 和本批任务的身份列表。
   IndexService 是唯一的写入者，检查和写入在它的单线程写入队列里按顺序执行，所以不存在两个写入者同时检查、再先后写入的竞争问题。
   **写入状态按索引实例隔离**：重建期间新旧两个实例同时存在。同一个 `file_id + op_seq` 在旧实例中完成了，不代表在新实例中也完成了。因此：
   - 写入端序号表按 `(index_instance_id, file_id)` 管理，每个实例一张；
   - 索引写入任务带有**目标 `index_instance_id`**，SQLite 中的完成记录也记录目标实例。重建期间，对同一个文件的变更，旧实例和新实例各有一条写入任务、各自确认；
   - 提取结果可以在两个实例之间复用（按 extract_key），但“已写入”状态不能共用；
   - 切换实例之后才返回的迟到任务，提交前要检查它的目标实例：目标不是当前有效实例、也不是正在重建的实例，就直接丢弃；不能把旧实例的完成状态当作新实例的完成状态。

   **写入端已应用序号不能只查 Searcher**：Tantivy 未 commit 的写入对 Searcher 不可见，commit 之后已有 reader 的刷新也不是同步完成的。所以写入端在内存中维护一张 `file_id → applied_seq` 表，**包含本批还没 commit 的操作**：
   - 启动时，在写入开始之前，用一个刚打开的 reader（它和最近一次 commit 完全一致）读取 `applied_seq` 字段来初始化这张表；
   - 每写入一个操作，立即更新表；
   - commit 成功后，表里的值成为已持久化的状态；
   - 如果 commit 前崩溃，未提交的写入全部丢失，重启时按上面的方式重建这张表，对应的任务在 SQLite 中仍然是未确认状态，会被重新执行。
   - **M0 补充**：删除操作保留只含 file_id、applied_seq、live=0 等必要字段的最小墓碑，不保留正文/锚点，确保重启后删除序号仍可恢复。进入 commit 发布前再次核对最新 op_seq 和租约；过期租约对应的最新任务必须重新排队，不能误标为已被新操作替代。
   - **commit 失败、但进程没有退出**（例如磁盘写满）：这时内存表已经推进了，如果直接重试，任务会被“大于已应用序号”的条件挡住。处理步骤：
     1. 立即暂停这个实例的写入队列；
     2. 回滚 writer（丢弃未提交的操作）。回滚失败，就关闭后重新打开 writer；
     3. 用一个新打开的 reader，从最后一次成功 commit 的持久化状态重建这个实例的序号表；
     4. 本批中所有未确认的任务恢复为待执行，等问题排除（例如腾出了磁盘空间）后再恢复写入并重试。
   - **commit 结果不确定**（例如调用超时，或者在返回之前收到了错误）：不能直接假定成功或失败。先重新打开 reader，读取当前持久化的 commit payload：如果其中的 `commit_batch_id` 就是本批，按成功处理，继续第 4 步的确认；如果不是，按失败处理，走上面的恢复步骤。
4. **同一个索引实例一次只允许一个“已提交但未确认”的批次**：上一批 commit 对应的 SQLite 确认完成之前，不允许提交下一批；确认失败，就暂停这个实例的提交，直到确认成功。这样崩溃后要补确认的永远只有最后一批，单靠最后一次 commit payload 就能完成恢复，不需要另建一套提交历史日志。
   commit 成功后，SQLite **只确认本批包含的那些任务**（按任务身份逐个确认）。更新文件的“已索引到第几个 op_seq”状态时，必须检查它仍然等于该文件当前的 op_seq；如果这期间文件又有了新的变更，就只记录已应用的序号，**不能把更晚的变更也标记为完成**。然后通知 reader 刷新，UI 才把新结果显示出来。
5. 如果在 commit 之后、SQLite 确认之前崩溃，启动时读取每个实例最后一次 commit payload 中的 `commit_batch_id` 和任务列表，和 SQLite 中该实例待确认的任务对比，幂等补记确认。根据第 4 步的规则，最多只有最后一批需要补确认；不在这一批里的未确认任务，重新执行。
6. 文件删除、索引范围移除，也走同一个流程。
7. **全量重建（追平后再切换）**：
   - 开始重建时，生成新的 `index_instance_id`，记录起点水位 `rebuild_start_jseq`，并对 FileCatalog 取一份快照，在后台建新索引；
   - 重建期间，旧实例照常接收增量更新、提供查询；`rebuild_start_jseq` 之后的 op_journal 记录保留，不被清理。重建本身也作为一个消费者，有自己的处理水位；
   - 新实例建完后，从 `rebuild_start_jseq` 开始回放 op_journal（文件变化、删除、范围调整、配置修改、提取器升级），一轮一轮追，直到和当前日志末尾的差距小于一个阈值；
   - **水位 W 的含义**：jseq ≤ W 的每一个操作，在新实例中要么已经提交，要么已经有明确的“待处理”或“失败”任务记录（随实例一起切换过去）。只是“已经入队”不算；
   - **切换步骤**：暂停写入队列 → 把剩余的操作补到 W → 新实例 commit → 在 catalog.sqlite 中用一个事务写入“当前有效实例 = 新 index_instance_id、水位 = W” → 写入目标和新查询的读取目标**同时**切到新实例 → 恢复写入队列。只切 reader 不切写入目标的话，后续更新会继续写进旧实例，这种情况不允许出现；
   - **重启时**以 catalog.sqlite 中持久化的“当前有效实例”为准，选择要打开的索引目录。未完成的重建实例在重启后按水位继续追，或者丢弃重来；
   - **旧实例的回收**：已经开始的查询仍然持有旧 Searcher，等这些查询释放后，再删除旧实例的目录；
   - 空间不足、重建失败、切换前崩溃时，有效实例标识不变，旧索引继续使用，不会被提前清空。

一次查询固定使用同一个 Searcher 快照。元数据里不长期保存 Tantivy 的 segment 或 doc 地址。

## 10. 文本提取能力矩阵

每种格式交付时都要包括**提取范围、位置锚点和测试样本**，不能只产出一个长字符串。

| 格式 | 阶段 | 提取方式 | 提取范围 | 位置锚点 |
|---|---|---|---|---|
| txt / md / csv / log / 代码 | M2 | Rust | 全文；编码支持 UTF-8/16（LE/BE/BOM）、GB18030、Big5，可按文件或目录手动指定编码；出现乱码时标记状态 | 行、列 |
| PDF（有文字层） | M2 | PDFKit | 逐页提取；**同时判断每页的文字层质量**，没有文字层的页标记为“等待 OCR” | 页 + 页内字符区间（+ PDFSelection） |
| DOCX | M2 | Rust（zip + XML） | 正文段落、**表格**、页眉页脚、脚注尾注、文本框；批注和修订可选 | 段落序号 / 表格单元格 |
| **DOC（旧版 Word）** | **M2** | worker 中用 `NSAttributedString(.docFormat)`，失败时退回 `textutil` 子进程 | 正文和表格文字（表格会被拍平成文本） | 段落序号；预览用 NSAttributedString 渲染 |
| XLSX / XLS | M3 | Rust `calamine`（同时支持新旧两种格式） | 显示值；公式、隐藏工作表、批注可选 | 工作表 + 单元格地址 |
| PPTX | M3 | Rust | 幻灯片文字、表格；备注可选 | 幻灯片编号 + 文本块 |
| OFD | M3 | Rust（zip + XML，解析 `TextCode`） | 逐页文字 | 页 + 坐标（可以在页面上高亮） |
| RTF / HTML / ePub | M4 | textutil / Rust | 正文 | 段落 |
| WPS（.wps） | M4 | 先用 .doc 的提取路线试；不行再调研 | 正文 | 段落 |
| 旧版 PPT | M4 | 调研后再定 | | |
| zip / 7z / tar 包内文件 | M4 | Rust，带“容器链”的虚拟路径 | 包内的子文件 | 子文件内的锚点 |
| 邮件 .emlx / .eml | M4 | Rust | 主题、发件人、正文、附件（附件作为子文档） | |
| 图片、扫描版 PDF | **M6** | Vision | 见第 14 节 | 文字框坐标 |

**提取结果复用（参考 fsearch、rga）**：下载目录里同一份公文的多个副本、改名或移动后的文件，不需要重新解析 .doc 或 PDF，直接复用已有的提取结果。

- **缓存键 = 原文件字节的强摘要（BLAKE3-256）+ 提取器标识及版本 + 提取配置的摘要**。提取配置包括：编码选择、是否纳入批注和修订、表格处理方式，以及以后 OCR 的语言和识别选项。
- 不能只凭一个 64 位短哈希相同，就认定两个文件的文本和锚点完全一样。如果为了加快查找而保留短哈希，命中后必须再比对完整摘要。
- 锚点的复用以“源文件字节相同 + 提取配置相同”为前提，**不能**因为“归一化后的文字相同”就复用锚点。
- **首版只做“复用提取结果，避免重复解析”，不做磁盘上的物理共享**：提取前，用 `extract_key` 在 Tantivy 中查找是否已经有文档带同样的键；有的话，读取它的 display_text、anchors、页级状态，**复制**进新文件自己的 Tantivy 文档，跳过解析。每个文件的文档仍然各自保存正文和锚点（与 D9 一致）。
- 这样不会引入跨文件的正文引用、共享对象的回收、额外的一致性协议。物理去重放到以后，等体积测试证明有必要时再做；到那时需要另外设计共享对象的存放位置、事务边界和恢复规则。
- 路径、权限、所属范围、收藏、结果条目、op_seq 都按文件分别管理。

资源上限：除了单文件大小，还限制解压后的字节数、压缩包条目数、嵌套深度、页数、提取出的文本长度、内存和执行时间。超过上限的文件标记为“部分索引”，不当作完整成功。类型识别：先用 UTType，再检查文件头魔数，不确定时跳过并记录原因。

## 11. 预览与定位

### 11.1 命中定位链

```
Match（file_id + revision + query_id + 匹配模式 + 区间 + 区间所属文本）
  ├─ 宽松模式：search_text 区间 ──norm_map──▶ display_text 区间
  ├─ 区分大小写：norm_cs 区间 ──它自己的映射──▶ display_text 区间
  └─ 严格原文：本身就是 display_text 区间（不再经过映射）
        ↓
        └─ anchors ─▶ SourceAnchor
              Text(行, 列)
              PDF(页, 页内字符区间, 可选矩形)
              Doc/Docx(段落 | 表格单元格)
              Sheet(工作表, 单元格)
              Slide(幻灯片, 文本块)
              OFD(页, 坐标)
              OCR(页或图片, 文字框, 坐标变换)   ← M6 才实现，枚举值现在就预留
```

- 偏移量统一用 Unicode 标量（字符）计数。跨过 Rust/Swift 边界时，统一换算成 UTF-16（NSRange），由共享测试保证（测试用例包括 `ﬁ`、组合字符、emoji、全角字符）。
- 预览前先核对文件版本。版本不一致时提示“索引版本待更新”，并把文件重新排队，**不会把旧的高亮画到新文件上**。

### 11.2 各格式的预览能力

| 类型 | 预览 | 不承诺 |
|---|---|---|
| 文本 / 代码 | 行号、命中跳转、可选语法着色 | 所有编辑器都支持“跳到指定行” |
| PDF | 原页面 + 选区高亮 | 旋转页和裁切框（CropBox）的情况需要单独测试 |
| DOCX / DOC | 带结构的文本（段落、表格），高亮命中处 | 和 Word 完全一致的排版、原文件的页码 |
| XLSX / XLS | 命中单元格附近的二维表格 | |
| PPTX | 幻灯片编号 + 文本块 | 让第三方应用跳到指定幻灯片 |
| OFD | 页面渲染（M3 实测后决定），否则显示结构化文本 | |

### 11.3 打开与定位

- `↵`：用默认应用打开。
- `⌘↵`：在 XSearch 的阅读窗口中打开，并定位到命中处。
- 对文本或代码文件，提供“在编辑器中打开到对应行”（VS Code、Sublime、Zed 等列在支持列表中）。
- 对 PDF，除了 XSearch 自带的阅读窗口，还提供“在外部应用中打开到对应页”：Skim 直接跳转；系统“预览”App 需要开启辅助功能权限，用模拟“前往页面”的方式跳转（参考 fnd，设置中可选）。
- 对 Office 文件，提供“打开并复制关键词”作为辅助操作，不保证对方应用的 `⌘F` 一定会用这个词。

## 12. 查询语法与开关

| 语法 | 阶段 | 设置开关 | 说明 |
|---|---|---|---|
| 普通输入 | M1 | — | 名称模式：子串；内容模式：字面子串 |
| `in 词` | M2 | — | 切换到内容模式，切换后在输入框里显示一个“内容”标签 |
| `dir:路径` | M1 | — | 目录范围，可以写多个；也支持把访达里的文件夹直接拖进输入框 |
| `ext:doc;docx`、`kind:doc` | M1 | — | 类型过滤 |
| `甲 乙`、`"甲 乙"`、`甲 \| 乙`、`-甲` | M2 | 运算符开关 | 两种模式共用 |

| `regex:…` | M3 | **正则开关** | 名称模式下在内存中匹配。内容模式下，**扫描已存储的提取正文**（和短查询扫描用同一套机制，遵守工作量预算、渐进返回和取消），需要搭配 `dir:`、`ext:` 等条件缩小范围；如果能从正则中提取出必须出现的字面片段（≥3 字节），先用它召回候选。M4 的“扫描原文件”只用于还没建索引的目录 |

| `"甲 乙"~N` | M3 | 邻近查询开关 | 见 8.6 |

开关关闭时，对应的符号按普通字符搜索。比如关闭通配符后，`*` 就是字面上的星号。按 `⌘/` 显示语法速查，里面会标出哪些语法当前已开启。

## 13. 交互

- **呼出**：默认快捷键 `⌥Space`（Option+Space），可在设置中修改。如果和其他应用冲突导致注册失败，在首次启动引导和菜单栏里提示用户改键；另外可以单独设置一个“直接进入内容搜索”的快捷键。面板呼出时获得键盘输入焦点，关闭后焦点还给原来的应用。
- **模式**：用 `⌘1` / `⌘2` 切换名称和内容，模式栏一直可见；切换时保留输入内容和范围。默认以名称模式呼出，可以在设置里改为“记住上次的模式”。
- **布局**：名称模式是窄长条；内容模式自动加宽成双栏，选中结果即在右侧预览；按 `⌘E` 展开为完整窗口（左侧范围树和过滤条件、中间可排序的结果表格、右侧预览），三种布局共用同一个 QuerySession、ResultModel 和 PreviewController。
- **输入法**：输入法还在组合（有 marked text）时，不触发搜索，也不拦截空格、回车和方向键。
- **快捷键**：
  - `Tab` 保留给焦点导航；
  - 空格只在结果列表获得焦点时触发 Quick Look；
  - 有选中文本时 `⌘C` 复制文本，复制路径用 `⇧⌘C`；
  - `Esc` 先关闭子弹层，再关闭面板；完整窗口点击外部时不会消失。
- **收藏**：`⌘D`，绑定 file_id（同时保存路径用于重新定位）。输入框为空时显示收藏和最近打开的文件。删除或重建索引不影响收藏。
- **结果列表**：先显示片段，选中文件后再计算总命中数（“第 n/N 处”）。
- **移到废纸篓**：`⌘⌫`，执行前弹出确认，放在 M3。

## 14. OCR（M6）与提前预留

**结论：OCR 放在最后是可行的，不需要提前实现。**前提是 M2 先预留以下三项，这样接入 OCR 时只需要新增提取器、按版本重排受影响的文件，不需要重建全部索引，也不需要改预览架构：

1. **锚点模型预留 OCR 类型**（11.1），预览组件支持“原图 + 叠加图层”的结构（M3 的 OFD 页面高亮会先用到这个结构）。
2. **页级提取状态**：混合 PDF 同时含有文字页和扫描页，文件级的 `source = text / ocr` 表达不了这种情况。从 M2 开始，每页单独记录：
   - 提取来源（text / ocr / 两者）；
   - 状态（完成 / 等待 OCR / 失败 / 部分）；
   - 提取器版本和提取配置摘要。

   页级状态**保存在每个文件自己的 Tantivy 文档中**（与 D9、第 10 节一致；复用提取结果时随正文和锚点一起复制），同时在 catalog.sqlite 中保留一份调度索引，供 OCR 补做时查询。没有文字层的页标记为“等待 OCR”，在结果和诊断页里显示出来，扫描页不会被悄悄当成“没有内容”。文件级的 `extract_state` 由页级状态汇总得出。
3. **`extractor_ver` 和 `source` 字段**，加上可暂停、可退避、能感知电源和温度的任务调度器（M2 处理大文件时本来就需要）。

M0-B 已做 Vision 小实验（见 M0 报告 5.6）：正文页识别质量好，目录/表格的阅读顺序是主要弱点；模型冷加载约 12 s，之后约 0.1–0.25 s/页；150 dpi 与 300 dpi 结果相近；远距离拍摄的屏幕照片识别不出文字。

M6 的设计要点：
- 用 `RecognizeTextRequest`（macOS 15 起就有），语言设为 zh-Hans、en-US，可以在设置中调整；对比测试 `RecognizeDocumentsRequest`（macOS 26），效果好就用它来获取段落和表格结构。
- 混合型 PDF 按页 OCR，文字层和 OCR 结果都标明来源，并去重。渲染分辨率按目标 DPI 和像素预算计算。
- 阅读顺序恢复和行拼接都保留映射，可以追溯到原始文字框；英文行尾的连字符不无条件删除。
- 编号、金额、代码这类内容不开语言纠错；第 2 候选默认关闭。
- 第一次有 OCR 任务时在 worker 中预热模型（冷加载约 12 s，期间显示进度）；渲染从 150 dpi / 长边 2000 px 起步；并发度从 1 开始实测；用电池或温度高时暂停 OCR。
- 识别出 0 个字符的页面显示“OCR 未识别出文字”，不显示成“没有结果”；置信度不当作准确率。
- 用户可以对指定文件强制 OCR。
- 二维码识别作为可选项。

## 15. 权限与隐私

- 首次使用不强制要求完全磁盘访问权限：先让用户选择可以访问的目录；遇到受保护的位置时，再说明原因并引导开启。签名后的主应用、XPC 服务、子进程整条访问链路，要在 M0 验证。
- 提取出的正文属于敏感数据：数据**目录权限 0700，普通数据文件权限 0600**；正文和搜索词不写入日志。
- **MCP 接口（M4，可选）**：默认关闭。只有用户主动启用、并逐个授权的客户端才能读取搜索结果和正文片段。结果一旦交给外部客户端，它怎么处理（例如发送给云端模型）不在“只在本机处理”的保证范围内，启用时要明确提示这一点。
- 可以重建的索引和不能重建的个人数据（收藏、历史、设置）分开存放；卸载和清理时，明确告诉用户会删除哪些数据。

## 19. 性能验收方法

以下是初始目标，在 M0 中用你的机器和真实语料校准。不使用其他项目在别的机器上的数字。

| 指标 | 初始目标 |
|---|---|
| 常驻状态下按快捷键到可以输入 | P95 < 50ms |
| 名称：输入到首屏结果 | P95 < 80ms（引擎耗时单独记录） |
| 内容：普通查询到首屏已核验结果 | P95 < 200ms（在公开的语料和查询集上测） |
| 选中文件到首个高亮出现 | 普通文档 P95 < 200ms；超大文档单独统计 |
| 小文本保存后可以被搜到 | 队列空闲时 < 3 秒 |
| 首次扫描 | 分别记录首批结果可搜的时间、全部完成的时间、冷缓存和热缓存 |
| 内存、索引体积、功耗 | 按进程分别记录空闲和峰值；体积按“倒排 / 正文 / 锚点”拆开统计 |

查询集要覆盖：中文一字、二字、三字；英文单词中间的子串；数字片段；标点；目录过滤；高频词；多条件组合；连续输入。

## 20. 风险与对策

| 风险 | 对策 |
|---|---|
| 所有文字都做 trigram，索引体积偏大 | M0 实测；trigram 只记录文档是否包含；用排除规则和大小上限控制范围。如果确实需要，可以提供“**按词索引的降级模式**”，但只能由用户对指定目录**主动开启**，界面上明确标注“该目录不保证任意子串搜索完整”，并列出不再保证的查询类型（单词中间的片段、数字片段、不足一个词的中文片段） |
| 单字、高频词的候选太多 | 先显示已核验的结果、有工作量预算、可以取消、明确显示“结果不完整” |
| .doc 提取质量不稳定 | NSAttributedString 和 textutil 双路线，M0 用真实样本对比；失败时显示状态 |
| 解析器卡死或崩溃 | 放在 worker 进程，设租约和超时，失败后退避，多次失败则隔离 |
| FSEvents 丢事件、索引过期 | 9.2 节的规则 + 定时对账 + 预览时核对文件版本 |
| 崩溃导致索引和 SQLite 不一致 | 9.3 节的提交协议、写入端序号表、幂等重放、索引实例切换 |
| 用户搞不清为什么搜不到 | 诊断页 + 结果中显示各种状态 |

## 21. 待定事项

- M0-B 已定方案：内容召回使用字节 trigram；2 字节默认前缀区间 + 末尾特殊项，保留范围扫描对照；布隆默认关闭；正文使用 Tantivy Zstd stored fields（16 KB 块 + 块缓存），不另建正文存储；文件名使用目录块深度优先 + 名称驻留 + 后台合并的增量层，不用字符类位图；IndexService 在应用启动时预热（XPC 冷启动约 16 ms，稳态往返几十微秒）；DOC 采用 NSAttributedString，保留 textutil 兜底；DOCX 使用 Rust ZIP/XML。
- 仍需真实数据决定：短查询的成本切换阈值、增量层合并阈值、真实磁盘的不同名称比例、大库上布隆是否值得启用。M0-B 的名称数据是合成的，内容语料只有 12 份真实文档，不能推断百万文件性能；M1/M2 用真实扫描复测。
